## Что это за проект

Business Watchdog — SaaS для обнаружения финансовых расхождений и поломок checkout в WooCommerce-магазинах. Laravel модульный монолит + WooCommerce-плагин + Stripe read-only + изолированный Playwright-воркер. ИИ не реализуется. Полное ТЗ — `spec/Business-Watchdog-TZ.md`, порядок чтения — `AGENTS.md`.

## Этап разработки

Репозиторий сейчас в фазе **D1–D5 бэкенд-слайсов** (по внутренней нумерации шагов `docs/progress.md`, не всегда совпадает 1:1 с разделом 36 ТЗ). P0 pilot пока не достигнут — минимальный кабинет, браузерные проверки и email ещё не реализованы.

Реализовано (backend, `apps/backend`, до Step 44 включительно):

- Локальный инфраструктурный bootstrap (Docker Compose: PostgreSQL 18, Redis, S3Mock вместо MinIO, Mailpit).
- Auth/tenancy: регистрация, membership/roles; с Step 39 — Sanctum SPA-сессии (`statefulApi`), CSRF на `api/*`, сессии в БД, лимиты login 5/мин и signup 3/час.
- Store pairing: pairing code (с Step 40 — лимит 20/час/IP и audit неудачных попыток), HMAC-подписанные credentials (keyring с версиями ключей шифрования, ротация с 24ч draining), store verification (с Step 42 — реальная проверка DNS TXT / connector challenge через SSRF-безопасный клиент, активация магазина, запрет browser checks до проверки).
- Durable event ingestion (с Step 41 — полная JSON Schema Draft 2020-12 валидация через `opis/json-schema`): `event_inbox`, idempotency, обработка дублей/конфликтов revision, лимиты батча, quarantine невалидных событий.
- Projections: orders/order_revisions/refunds/payments/financial_transactions из нормализованных событий.
- Domain outbox: dispatcher, exponential backoff, sweeper для истёкших lease, bounded loop команда `outbox:dispatch`.
- Integration lifecycle: list/detail/revoke endpoints, audit log (`audit_log`).
- Payment/refund allocation foundation: таблицы `payment_allocations`/`refund_allocations`, `PaymentAllocationService` с блокировками строк и проверкой сумм.
- Allocation revoke/unlink: `PaymentAllocationService::revokeCaptureAllocation()`/`revokeRefundAllocation()` — reason обязателен, повторный revoke запрещён, revoke capture allocation блокируется активными refund allocations на неё, каждый revoke пишет `audit_log`.
- Reconciliation foundation: таблицы `reconciliation_runs`/`reconciliation_findings`, `OrderReconciliationService::evaluate()` — считает G/C/RW/RP по одному заказу. Правила: `MONEY_UNSUPPORTED`, `MONEY_CAPTURE_MISSING`, `MONEY_CAPTURE_AMOUNT`, `MONEY_REFUND_MISSING`, `MONEY_REFUND_EXTRA`, `MONEY_MULTIPLE_CAPTURES`, `MONEY_CURRENCY_MISMATCH`, `MONEY_ORDER_CHANGED` (все — per-order, несмотря на то, что три последних сначала казались store-wide). `MONEY_PAYMENT_WITHOUT_ORDER` — единственное действительно store-wide правило, отдельный `UnmatchedPaymentScanner`. Все 9 rule-кодов раздела 14 ТЗ покрыты. Синхронно, без scheduler/nightly sweep/dirty-order coalescing.
- Публичный API allocation + reconciliation: `POST /payment-allocations[/{id}/revoke]`, `POST /refund-allocations[/{id}/revoke]`, `POST /stores/{id}/reconciliations`, `GET /stores/{id}/findings`. Новая инфраструктура `Idempotency-Key` (`idempotency_keys` таблица + middleware, reserve-then-run mutex через unique constraint) обязательна на всех create/trigger-мутациях. По ходу закрыт реальный пробел в `PaymentAllocationService::allocateRefund` — refund и payment_allocation теперь должны принадлежать одному заказу (`ERROR_ORDER_MISMATCH`).

- Детальные GET-эндпоинты: `GET /orders/{id}` (поля заказа + последний finding по каждому rule_code + captures/refunds/refund_transactions/allocations/revisions), `GET /payments/{id}` (аналогично для платежа), `GET /stores/{id}/unmatched-payments` (подсказки exact_candidate/manual_review для orphan-captures, read-only, ничего не пишет). Общий `App\Support\Api\UuidCursor` для курсорной пагинации.
- Incident engine (money family): таблицы `signals`/`incidents`/`incident_signals`/`incident_activity`/`suppressions`. `MoneyIncidentCorrelator` открывает/привязывает инциденты по mismatch-findings, авто-резолвит по свежему ok-finding, реоткрывает в течение 24ч после resolve или создаёт новый инцидент после. Fingerprint группирует rule_code в более крупный `component` (`capture`, `refund`, ...) — иначе переход MONEY_CAPTURE_MISSING→MONEY_CAPTURE_AMOUNT после починки никогда бы не авто-резолвился. `IncidentLifecycleService`: acknowledge/resolve/comment/snooze/revoke-suppression. Подключено в `ReconciliationController::store()` — каждый trigger автоматически обновляет инциденты. Публичный API: `GET /incidents[/{id}]`, `POST /incidents/{id}/acknowledge|resolve|comments|snooze`, `POST /suppressions/{id}/revoke`.

- Email/Telegram-уведомления (раздел 23 ТЗ, P0/P1-часть): таблицы `notification_channels`/`notification_deliveries`/`notification_channel_verifications`. Переход инцидента (open/reopen/auto-resolve) в той же транзакции пишет `incident.notification_requested` в outbox; outbox-диспетчер раскладывает его в delivery на каждый включённый и подтверждённый канал (фильтр магазинов, порог severity, recovery opt-out, quiet hours, suppression → `suppressed`). Worker `notifications:deliver`: retry 1м/5м/15м/1ч/6ч + Retry-After, dead letter после 24ч с health канала, timeout → `uncertain` без автоповтора. Шаблоны ru/en/de без PII. API: `/notification-channels` (email с кодом подтверждения; Telegram pending channel с binding code), secret-protected `/webhooks/telegram/bind` and native `/webhooks/telegram/updates`, PATCH, verify email, test раз в минуту, `GET /notification-deliveries`. Step 88 добавил Telegram sender через Bot API и UI привязки; Step 89 усилил binding code lookup против активных глобальных коллизий; Step 90 добавил native Telegram update webhook, который сам извлекает код из сообщения; Step 91 зафиксировал Telegram sender failure semantics тестами; Step 92 добавил operator command для set/info/delete Telegram Bot API webhook с secret token; Step 94 прошёл live smoke: реальный бот через Cloudflare webhook привязал чат по коду и доставил тестовое сообщение; Step 95 добавил opt-in reminders открытых инцидентов (`reminder_hours`, `incident_reminder`, команда `notifications:remind`) с учётом quiet hours и настройкой в кабинете. Решения — `docs/adr/0002-notification-delivery-decisions.md` (владелец принял как есть 2026-10-09).
- Фоновая обработка (Step 38): «грязные» заказы (`reconciliation_dirty_subjects`) помечаются в транзакции проекции события и при создании/отзыве allocation, коалесинг 30 с; `reconciliation:process-dirty` пересчитывает их и обновляет инциденты (а значит и уведомления) без ручного вызова API. Повторная проверка в момент окончания grace. Ночной sweep 90 дней раз в сутки (02:30 UTC) с уникальным окном в `scheduled_job_windows`. Laravel scheduler: outbox каждые 10 с, dirty и уведомления каждые 30 с, reminder planner раз в час; в Docker Compose добавлен сервис `scheduler`. Решения — `docs/adr/0003-scheduler-and-dirty-reconciliation.md`.

- Шлюз покрытия провайдером (Step 48, ADR 0006 п.1): без активной интеграции `independent_provider` сверка заказа даёт `MONEY_UNSUPPORTED` / `unknown` / `provider_not_connected` и не открывает инцидентов; сканер платежей без заказа и allocation работают только с данными независимого провайдера; приём событий отклоняет `independent_provider` от ключа плагина (`source_authority_not_permitted`); отзыв провайдера ставит окно 90 дней магазина на пересчёт.

- Наблюдение реальных попыток оплаты, слой 1 (Step 49, ТЗ §17.1, ADR 0007): плагин фиксирует попытки Classic и Store API/Blocks и их исходы (`paid`, `on_hold`, `failed` с классом, `pending_stuck` 30 мин, `late_success`, `rejected_before_order`) и раз в 5 минут шлёт окна `checkout.payment_attempts` по способам оплаты, без PII. Бэкенд проецирует окна в `payment_attempt_windows`; правило `CHECKOUT_PAYMENTS_FAILING` (3 подряд неуспешных по способу оплаты) открывает инциденты семейства `checkout_payment` с уведомлениями и закрывает их при успешной оплате. Проверено настоящими HTTP-оформлениями заказов на всех 6 версиях WooCommerce.

- Свежесть коннектора (Step 50, ACC-14, ADR 0009): heartbeat сохраняет самоотчёт плагина (backlog, самое старое неотправленное событие, версия); `integrations:check-freshness` раз в минуту помечает коннектор `stale` (3 пропущенных heartbeat) или `partial` (отставание доставки > 1 ч), переводит интеграцию в `degraded` и открывает инцидент «нет данных от плагина — это не остановка продаж». Пока данные магазина неполные, сверка денег даёт `unknown/store_data_stale`; при восстановлении инцидент закрывается и окно заказов пересчитывается. Общий `IncidentRecorder` для не-денежных инцидентов.

- Браузерные проверки — бэкенд (Step 51, ТЗ §18–20, ADR 0010): сценарий `payment_form` на магазин, планировщик `browser:schedule` (15 мин ±10 %, один активный запуск), внутренний протокол для воркера `/internal/v1/browser` (lease с `SKIP LOCKED`, fencing, heartbeat с абсолютным дедлайном, идемпотентный result, восстановление истёкших), политика исходов (сбой подтверждают только 2 `site_failure`, ошибки воркера — `inconclusive`), инциденты семейства `checkout` и инциденты покрытия, API сценария и ручного запуска. Воркер (Step 52, ADR 0011): `apps/browser-worker` — Node + Playwright 1.55 в официальном образе, песочница Chromium включена; адаптер WooCommerce распознаёт Classic и Blocks; сетевая политика пропускает только операции корзины и блокирует оформление заказа, order-pay, capture и refund; на всех 6 версиях WooCommerce проходит путь до формы оплаты без единого заказа, без способов оплаты даёт `site_failure`. Step 53 (ADR 0012): подписанный synthetic-маркер (ключ выводится из секрета спаривания магазина, уходит только на origin магазина, плагин проверяет подпись, помечает заказы, исключает их из попыток оплаты и удаляет только свои старые черновики Blocks); egress-прокси Squid (только HTTPS 443, приватные адреса запрещены после резолва), воркер изолирован сетями от БД и Redis. Step 54 (ADR 0013): скриншот при неуспешной проверке с закрашенными полями, iframe и адресами; загружается через внутренний API под арендой (воркер не получает доступа к хранилищу), хранится приватно 30 дней, пользователю — ссылка на 60 секунд.

342 теста: на SQLite 338 проходят + 4 PostgreSQL-only пропускаются; на PostgreSQL 18 (`make backend-test-pgsql`) проходят все 342 (`php artisan test` на PHP 8.4). Все новые миграции (reconciliation, idempotency_keys, incident engine, notifications, scheduler) проверены и накатаны на реальной PostgreSQL 18 в локальном Docker. Email проверен только через `Mail::fake`/тестовый sender, не через реальный SMTP.

Отклонения из ADR 0001 закрыты или формализованы в Steps 39–44 (у каждого пункта есть Resolution); локальное S3 — `docs/adr/0004-local-object-storage.md` (MinIO больше не раздаётся публично, остаётся S3Mock). Остальные решения — ADR 0002 (уведомления), ADR 0003 (scheduler).

WooCommerce-плагин (`plugins/woocommerce-watchdog`, Step 45): фундамент — слой совместимости по возможностям (HPOS/legacy, classic/blocks, Action Scheduler/WP-Cron), локальные таблицы, pairing, подписанный heartbeat с ротацией, публичный challenge. Нижняя граница по решению владельца: PHP 7.4 / WP 5.9 / WC 6.0 (ADR 0005). Docker-матрица из 6 целей (WC 6.0.2 … 11.2.0, legacy и HPOS) + e2e с бэкендом — всё зелёное; проверенные комбинации в `docs/compatibility.md`. С Step 47 плагин доставляет события в бэкенд (батчи, retry, dead letter, suspend), делает rescan 48ч каждые 15 мин, backfill 90 дней и шлёт capabilities/deployment события; e2e на всех 6 версиях WooCommerce доходит до проекций бэкенда.

**Step 103 — вход в админку для сотрудников сервиса (ADR 0034):** `/owner` в `apps/frontend/control`, API `/platform-api/v1` со своей сессией и CSRF-cookie (клиентская сессия не принимается), пароль + обязательный код аутентификатора, неактивность 30 мин / максимум 8 ч, аудит входов в `platform_audit_log`. Первый владелец создаётся на сервере: `php artisan platform:create-owner <email>` (пароль вводится скрыто, аутентификатор подключается там же, резервные коды показываются один раз). Каркас панели с разделами из ТЗ (пока заглушки). Живая проверка входа в Chromium (`apps/frontend/control/tests/e2e/run-login.sh`) — PASS. Тесты: SQLite 447 + 4 пропущено, PostgreSQL 18 451/451, админка 4/4, кабинет 98/98. **Следующий шаг:** раздел «Тарифы и скидки» — пакеты, цены, периоды оплаты, лимиты, пробный период, публикация в Paddle; затем скидки.

**Step 104 — тарифы в панели владельца (ADR 0035):** `/owner/plans` — создание пакетов, черновик версии (названия и описания ru/en/de, функции, лимиты, пробный период до 365 дней), цены с любым периодом (каждые 1–365 дней/недель/месяцев/лет), публикация с причиной и кодом из приложения (товар и цены создаются в Paddle), новая версия (старая снимается с продажи, подписчики остаются на своих условиях), снятие с продажи. Клиентам видны только опубликованные версии. Живая проверка в sandbox Paddle — PASS. **Следующий шаг:** скидки (процент/сумма, промокод или конкретному клиенту, срок, лимит использований, тарифы, число периодов).

**Step 105 — скидки в панели владельца (ADR 0036):** `/owner/discounts` — промокоды, скидки выбранным организациям и акции для всех; процент или сумма; один платёж / N периодов / навсегда; лимит использований, даты, тарифы. Скидку применяет только наш сервер (код > скидка организации > самая выгодная акция). В кабинете — поле промокода и цена со скидкой. Живая проверка в sandbox Paddle: промокод создан в админке и оплачен (28,00 € → 22,40 €), скидка в подписке на 2 периода — PASS. **Следующий шаг:** по выбору владельца — смена тарифа/отмена подписки в кабинете, подписки и клиенты в админке, публичный сайт с ценами.

**Step 106 — скидки складываются (решение владельца 2026-10-12, ADR 0036):** акция → личная → промокод, каждая от остатка после предыдущей; у каждой свой срок. Paddle принимает одну скидку, поэтому сервер отправляет одну общую: на покупку — разовую на транзакцию, на каждое продление `billing:plan-discounts` (каждые 15 мин) ставит подписке скидку на один следующий период. Каждый период записывается с расшифровкой (до, каждая скидка, итог) — вкладка «История скидок» в админке; в кабинете видна каждая скидка по очереди. Живая проверка в sandbox: 28,00 € → 25,20 € → 20,16 € оплачено, второй период тоже 20,16 € — PASS. **Следующий шаг:** по выбору владельца — смена тарифа/отмена подписки в кабинете, подписки и клиенты в админке, публичный сайт с ценами.

**Step 107 — подлинность исходящей почты:** адрес возвратов `MAIL_RETURN_PATH`; DKIM-подпись всех писем сервисом (`MAIL_DKIM_*`) или провайдером (`MAIL_DKIM_PROVIDER_MANAGED=true`); если ключ не читается, письма уходят без подписи с записью в лог, а не останавливаются. `php artisan mail:auth-check --strict` проверяет SPF, DKIM (ключ читается и совпадает с DNS), DMARC и выравнивание доменов; инструкция — README «Почта». Тесты: SQLite 468 + 4 пропущено, PostgreSQL 18 472/472. Проверено тестами и отправкой через SMTP в локальный Mailpit с проверкой подписи независимым верификатором; настоящий почтовый провайдер и публичный DNS не проверялись — нужен домен владельца. **Следующий шаг:** по выбору владельца — смена тарифа/отмена подписки в кабинете, подписки и клиенты в админке, публичный сайт с ценами.

**Step 108 — смена тарифа и отмена подписки в кабинете (ADR 0037):** превью смены (Paddle считает доплату за остаток периода, наш расчёт — следующий платёж со скидками, токен на 10 мин) и подтверждение; более дорогой тариф — сразу с доплатой (если оплата не прошла, ничего не меняется), более дешёвый — со следующего периода (у Paddle состав меняется сразу без списания, у нас оплаченный тариф держится до конца периода; `billing:plan-changes` каждую минуту); отмена запланированной смены; отмена продления в конце периода с объяснением и необязательной причиной; возобновление. Скидки следующего периода пересчитываются на новый тариф. Если новый тариф включает меньше магазинов — владелец выбирает, какие продолжат проверяться, остальные на паузе (не удаляются); без выбора браузерные проверки организации стоят. Тесты: SQLite 479 + 4 пропущено, PostgreSQL 18 483/483, кабинет 107/107, smoke 42/42; живой прогон в sandbox Paddle (покупка → повышение с доплатой 21 € → понижение → отмена понижения → отмена → возобновление) — PASS. **Ждут владельца (ADR 0037 п. 3, 4, 6, 7):** понижение через немедленную смену состава в Paddle без списания; доплата за остаток периода без скидок; скидки, ограниченные тарифом, не действуют на другом тарифе и не расходуются; пауза лишних магазинов. Не сделано: смена периода оплаты и валюты, портал способа оплаты, счета. **Следующий шаг:** по выбору владельца — подписки и клиенты в админке, публичный сайт с ценами.

**Step 109 — клиенты и подписки в админке (ADR 0038):** `/owner/tenants` — список организаций (поиск по названию, ID или подтверждённому e-mail владельца; фильтры по сервису, подписке, отмене, окончанию пробного периода), доступ и оплата показаны отдельно; карточка организации: обзор, магазины (только сводка, без находок и скриншотов), подписка (договоры Paddle, смены тарифа, временный доступ), сотрудники, аудит; `/owner/subscriptions` — все подписки. Действия владельца сервиса с просмотром последствий, причиной, кодом из приложения и аудитом: приостановить/возобновить сервис (оплата не трогается), временный доступ по тарифу до 180 дней и отзыв, продление нашего пробного периода до 90 дней, отмена подписки в конце периода, обновление из Paddle. Поддержка видит e-mail замаскированным и без данных об оплате. Тесты: SQLite 486 + 4 пропущено, PostgreSQL 18 490/490, админка 17/17; живая проверка в Chromium (`run-live.sh tenants`) — PASS. Не сделано: напоминание об оплате, вкладка счетов и оплат, доступ поддержки к деталям магазинов, «последняя активность». Матрица `spec/PANELS-ACCEPTANCE.md` частично устарела (EXT-01…12 не обновлены после Steps 98–106). **Следующий шаг:** публичный сайт с ценами или по выбору владельца.

**Step 110 — решения владельца по ADR 0038:** п. 4–6 приняты (приостановка не трогает оплату — возможно, пересмотрим; временный доступ до 180 дней, один за раз; продление нашего пробного периода до 90 дней, дату первого списания в Paddle не сдвигаем). Исправлено: временный доступ поверх оплаченного тарифа больше не понижает лимиты — по каждому лимиту берётся более выгодное значение. Тесты: SQLite 487 + 4 пропущено, админка 17/17.

**Step 111 — публичный сайт (ADR 0039):** страницы отдаёт Laravel готовым HTML (SSR, Blade), Node на сервере не нужен; `apps/frontend/public` собирает только стили в `apps/backend/public/site` (собирать при выпуске). Адреса `/{ru|en|de}`, `/{lang}/pricing`, `/{lang}/contact`, `/{lang}/{slug}` и `/{lang}/{slug}/{slug}`; `/` — по языку браузера. В админке «Сайт»: главная, тарифы и обратная связь (системные, со встроенным текстом, пока свой не опубликован) и свои страницы — адрес задаётся при создании, вложенность до двух уровней, текст на каждом языке, HTML-код с живым предпросмотром, черновик → публикация с причиной, все опубликованные версии хранятся (восстановление в черновик, снятие, удаление). HTML очищается (без скриптов, iframe, форм, обработчиков и style). Страница тарифов — из опубликованного каталога (годовая цена как есть + «примерно в месяц», выгода только против помесячной цены того же тарифа; примеры Free/Start/Pro только в тестовом режиме). Форма обратной связи: скрытое поле от ботов, 5 в час с IP; «Обращения» в админке (статус, заметка), письмо владельцу (`site:contact-notify`), удаление закрытых через 365 дней (`site:contact-purge`). Тесты: SQLite 494 + 4 пропущено, PostgreSQL 18 498/498, админка 22/22, кабинет 107/107; живая проверка в Chromium (`run-live.sh site`) — PASS. ADR 0039 п. 7–12 владелец принял «пока так» (примеры тарифов в тестовом режиме, права, правила формы, получатели писем, хранение 365 дней, кэш 60 с). Не сделано: привязка согласия с условиями к версии документа при регистрации/оплате, загрузка картинок, sitemap/robots, публичная регистрация (кнопка «Выбрать тариф» ведёт в кабинет). 

**Step 112 — масштабирование синхронизации и сверки (ADR 0040):** команды `stripe:sync`, `paypal:sync`, `woocommerce-api:sync`, `shopware:sync` теперь только ставят по заданию на подключение в очередь Redis `sync`; их выполняют обработчики `queue:work` (сколько угодно, одно подключение никогда не синхронизируется дважды одновременно; `--inline` — по-старому в одном процессе). Сверку разбирают непрерывные обработчики `reconciliation:work` (параллельно, `SKIP LOCKED`). **Обработчики обязательны в проде** (Docker: `sync-worker`, `reconciliation-worker`; в образ добавлен `pcntl`). Текущий результат каждого заказа — в `reconciliation_subject_states`; повторная проверка без изменений не пишет историю и не трогает инциденты. Ночной проход (выбор владельца): только заказы, результат которых может измениться, плюс заказы «своей» ночи 30-дневного цикла (Step 113) — каждый заказ полностью раз в 30 дней. Исправлено попутно: горячий цикл перепроверки заказа в ожидании, огромный список id в скане платежей без заказа, устаревшие «текущие находки». Замер локально (PostgreSQL в Docker): 1 обработчик ~62 заказа/с с записью и ~119/с без изменений, 4 обработчика ~290/с (было ≤ 100 за 30 с). Тесты: SQLite 503 + 4 пропущено, PostgreSQL 18 507/507; живая проверка очереди с Redis и sandbox Stripe/PayPal и двух обработчиков сверки — ок. **Следующий шаг:** по выбору владельца.

**Step 113 — исправления по ревью Step 112:** раздача заданий синхронизации больше не пропускает и не дублирует подключения (список ID читается одним запросом до постановки заданий, а не постранично по меняющемуся времени синхронизации); перепроверка каждого заказа теперь гарантированно раз в 30 дней (постоянный «день цикла» `recheck_slot` у каждого заказа + подхват просроченных, если ночь не выполнилась). Тесты: SQLite 505 + 4 пропущено, PostgreSQL 18 509/509. **Следующий шаг:** по выбору владельца.

**Вариант цен (ADR 0041, предложение, не реализовано):** пакеты по объёму заказов магазина в месяц (пример: Start до 1 000 — 19 €, Business до 5 000 — 39 €, Growth до 20 000 — 79 €, Enterprise — индивидуально), функции защиты во всех платных пакетах, магазины/частота проверок/хранение — лимиты пакета, частые проверки — доплата; при превышении — уведомление и время на переход, считаются только уникальные новые реальные заказы (среднее за 3 месяца). Цены — пример, нужна проверка по себестоимости. Текущий счётчик событий для этого не подходит (считает все события).

**Step 114 — пакеты по объёму заказов (ADR 0041):** счётчик новых реальных заказов магазина по месяцам (повторы, смены статуса, возвраты и заказы до добавления магазина не считаются), среднее за 3 полных месяца; в админке в версии пакета — лимит «Заказов в месяц на магазин», льготный период (дней) и «Цена индивидуально» (публикуется без цен). Ежедневно `billing:order-volume`: при превышении — отметка, одно письмо владельцу с датой и рекомендация пакета; ничего не отключается и не списывается. Видно в кабинете (блок «Объём заказов»), в карточке клиента в админке и на странице цен. Тесты: SQLite 511 + 4, PostgreSQL 18 515/515, админка 23, кабинет 108. **Следующий шаг:** доплата за частые проверки (новый вид цены через Paddle), хранение истории по пакету.

**Step 115 — пауза после льготного периода (решение владельца):** пауза на уровне организации (подписка — у организации): после льготного периода организация приостанавливается (`paused_billing`, причина `order_volume_exceeded`) — проверки, сверка, наблюдение за оплатами и уведомления стоят, данные магазинов принимаются; письмо владельцу. Снимается только когда пакет покрывает объём всех магазинов — сразу после покупки/смены пакета или временного доступа, сверка перепроверяется. Правило истории принято. Тесты: SQLite 513 + 4, PostgreSQL 18 517/517, фронтенды зелёные. **Следующий шаг:** доплата за частые проверки, хранение истории по пакету.
