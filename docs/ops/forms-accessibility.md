# Доступность входа, регистрации и обратной связи

Область: `/app/login`, `/owner/login` (пароль и MFA), `/{ru,en,de}/signup`, `/{ru,en,de}/contact`. Изменения локально проверяются перед выкладкой; это не заявление о полной сертификации WCAG всего продукта.

## Поведение

- Поля имеют доступные имена, `name` и подходящие `autocomplete`. Вход читает значения из формы при отправке, включая автозаполнение без `input/change`. Пароли и коды можно вставлять; показ пароля сохраняет `autocomplete`. Код MFA остаётся текстовым, поскольку допускаются буквенные коды восстановления.
- Пустая форма входа объясняет ошибки. Сводка получает фокус, ссылки переводят его в поля, ошибки связаны через `aria-describedby`/`aria-invalid`. MFA получает фокус при переходе; возврат переводит его в пароль; отмена passkey возвращает его на кнопку. Ошибки сети допускают повтор, повторный запрос во время отправки блокируется, пароль после запроса очищается.
- Регистрация и обратная связь используют обычные HTML POST и работают без JavaScript. Нативная проверка обязательности/формата дополняет серверную; серверные ошибки имеют сводку со ссылками и фокусом. Несекретные значения сохраняются; пароли и файлы после серверного отказа надо ввести/выбрать заново. Успех обратной связи получает фокус.
- Небольшой Vite-модуль добавляет показ пароля, проверку совпадения паролей и размера файла, состояние отправки и восстановление кнопки при возврате в истории. Модуль загружается с CSP nonce и не использует HTML/ScriptURL sinks.
- У обратной связи есть текст того же математического задания: кнопка при JS, ссылка в новую вкладку без JS. Новый web GET `/{locale}/contact/captcha/text` возвращает локализованный `text/plain`, `no-store`, `nosniff`. Картинка и текст не меняют задание друг у друга. Прежние TTL, однократная проверка, honeypot, серверные ограничения частоты и проверка вложений сохраняются. Чтение текста не проверяет и не расходует ответ. Это простая защита от спама: текст облегчает автоматическое решение; она не гарантирует защиту от ботов. Вход и регистрация капчи не получают.
- Исправлены контраст подписи подвала на страницах форм, подчёркивание ссылок в тексте и размер целей ссылок в сводке ошибок. Поля не выходят за ширину формы при 320 CSS px.

Миграций и изменений JSON/OpenAPI контрактов нет. Новый маршрут — web endpoint с сессией, без tenant данных. Семантика авторизации, MFA, согласия с актуальными документами и безопасного хранения вложений не меняется.

## Воспроизводимая локальная проверка

Нужны Node из `apps/frontend/package.json`, зависимости frontend/browser-worker, Playwright 1.55.0 и локальные postgres/mailpit. Почта обязательно остаётся в Mailpit. Команды из корня репозитория:

```sh
npm --prefix apps/frontend run check
docker compose up -d postgres mailpit
docker compose exec -T postgres createdb -U bw_app bw_forms_a11y
# Создание базы нужно только один раз; не использовать migrate:fresh на общей базе.
docker compose run --rm --no-deps -e DB_DATABASE=bw_forms_a11y backend-cli php artisan migrate --force
docker compose -f docker-compose.yml -f infra/dev/forms-a11y.compose.yml up -d forms-backend forms-web
docker exec bw-forms-backend php tests/Browser/forms-fixture.php
node apps/frontend/scripts/forms-a11y-smoke.mjs
```

Фикстура откажется работать вне local/testing и вне `bw_forms_a11y`. `serve --no-reload` обязателен: иначе Laravel CLI удаляет Docker-переменные дочернего сервера, который заново читает `.env`. Доверие прокси `*` задано только этому локальному сервису. Сессионные cookies — Secure, SameSite=Lax и host-only: WebKit отвергает `Domain=localhost`. Внешний URL должен оставаться `https://localhost:8443`; скрипт отказывается работать с другим hostname. Используются синтетические адреса `example.test`, локальные документы и отдельный сотрудник; команда генерации MFA-кода сбрасывает replay marker только у этого тестового сотрудника. Скрипт создаёт аккаунты и обращения, читает письма через локальный Mailpit и запускает доставку уведомлений из изолированной базы.

Если бинарник WebKit не запускается на хосте, использовать уже собранный образ browser-worker с тем же Playwright и сетевым туннелем только для loopback:

```sh
docker compose --profile browser build browser-worker
docker compose -f docker-compose.yml -f infra/dev/forms-a11y.compose.yml up -d forms-webkit
BW_FORMS_WEBKIT_WS=ws://127.0.0.1:3001/ node apps/frontend/scripts/forms-a11y-smoke.mjs
```

После пересборки SPA перезапустить `forms-web`, чтобы Caddy перечитал CSP хеши. Не пересобирать кабинеты во время прогона. Для остановки только тестовых сервисов:

```sh
docker compose -f docker-compose.yml -f infra/dev/forms-a11y.compose.yml stop forms-backend forms-web forms-webkit
```

## Проверки и пределы evidence

Backend: `ContactFormTest`, `PolicyAcceptanceTest`, `PublicSiteTest`, `PublicStorefrontCheckTest`, `SecurityHeadersTest`; frontend: `loginAccessibility.test.ts` в обоих кабинетах плюс существующие suites, типы и сборки. Браузерный скрипт проверяет полные страницы и ошибки через axe (`wcag2a`, `wcag2aa`, `wcag21aa`, `wcag22aa`), порядок Tab/видимый фокус, ссылки ошибок, локализацию, reflow 320 px, CSP, регистрацию с подтверждением адреса, настоящий вход клиента и сотрудника с MFA, ошибку капчи, PDF/слишком большой файл, доставку уведомления и SSR без JS. Часть проверок менеджера паролей моделируется установкой нативного `input.value` без событий — это не проверка конкретного менеджера паролей.

Основания: ТЗ §§7, 26, 35.5–38, ADR 0019/0039/0042, EXT-03 и EXT-27. Критерии WCAG, на которые направлены изменения: 1.3.1, 1.4.3, 1.4.10, 2.1.1, 2.4.7, 2.5.8, 3.3.1–2, 3.3.8. Нативная валидация допустима для обозначения ошибки и перевода фокуса ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/error-identification)); сводка и связанные поля следуют [W3C form errors](https://design-system.w3.org/styles/form-errors.html).

Остаются проверка озвучивания настоящими VoiceOver/NVDA, конкретными менеджерами паролей и аппаратным WebAuthn, а также smoke после выкладки на production. Автоматический axe и WebKit не заменяют эти проверки. Production не изменяется этим локальным прогоном.
