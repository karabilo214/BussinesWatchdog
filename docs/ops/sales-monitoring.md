# Диагностика истории продаж задачи 12

История — Step 323 / ADR 0091; журнал покрытия и исключения — Step 324 / ADR 0092. Это внутреннее чтение существующих проекций для подготовки нормы и калибровки. Детектор, пользовательский экран, автоматические уведомления и оценка потерь ещё не включены; тарифы не меняются.

Из `apps/backend` на Mac:

```sh
/opt/homebrew/opt/php@8.4/bin/php artisan sales:history --tenant=<tenant-uuid> --store=<store-uuid>
/opt/homebrew/opt/php@8.4/bin/php artisan sales:history --tenant=<tenant-uuid> --store=<store-uuid> --from=2026-10-29T00:00:00Z --to=2026-10-30T00:00:00Z --mode=live
```

В Docker PHP 8.4 используется тот же artisan command из каталога приложения. `--tenant` и `--store` обязательны и проверяются вместе. `--mode=live` по умолчанию, `test` — отдельный отчёт. Без дат — последние 28 суток до начала текущего UTC-часа. Явные даты — RFC3339 с секундой и смещением/`Z`; интервал `[from,to)`, положительный, не больше 28 суток, не в будущем. Все значения — идентификаторы своего тестового окружения, не примеры для запроса к production.

Вывод JSON содержит только идентификатор магазина, режим/часовой пояс, интервал, почасовые счётчики и причины непригодности для тревог; ссылок на заказы, transaction IDs и данных покупателей в нём нет. Границы часов UTC, локальная подпись с offset и днём недели магазина; два повторных часа DST различаются. Отметки оплаты магазина не называются независимыми списаниями; заказ с частичным capture тоже попадает в `orders_with_capture_observed`, поэтому это не число полностью оплаченных заказов.

Общее покрытие и baseline по-прежнему unknown, прогрев unverified_history и alerts_enabled=false. С Step 324 в каждом часе добавлен `metric_coverage`: созданные заказы могут иметь complete после полного API-чтения и обработки inbox; исторические paid-маркеры и capture остаются unknown. Нулевой счётчик при unknown не доказывает отсутствия продаж. Даже complete у созданных заказов не подтверждает покрытие независимых денег. Свежий heartbeat описывает состояние источника сейчас, а не историческую полноту. Deleted/synthetic/test (для live) исключены, дубли проекций одного заказа после переподключения не увеличивают счётчик. Повторный запуск не меняет БД. Команда `sales:history` не вызывает провайдеров, не запускает покупки, не создаёт инциденты и не включена в cron.

Команда может читать большую историю внутри одного магазина: перед автоматизацией нужны измерения на реальном объёме и журнал исторического покрытия. После миграции `2026_10_30_120000_add_sales_coverage_journal` существующие WooCommerce recent/audit и Shopware audit автоматически записывают доказательства чтения. Отдельное задание `sales:finalize-coverage` уже включено в scheduler раз в минуту: ручное включение владельцем не нужно. Оно не создаёт норму или тревоги. Неполное чтение, пропуски mapper и неприменённые ревизии оставляют покрытие неизвестным/awaiting_projection; соединённые интервалы не заполняют разрывы. Старые интервалы и пометки удаляются из 28-дневного горизонта.

`baseline_eligible` — кандидат данных созданных заказов, не принятая норма. Инциденты исключают целый локальный день; текущие паузы фиксируются автоматически и остаются после возобновления. Ввод пометок акций/праздников через кабинет и календарь DE ещё не готовы, новые серверные команды для этого владельцу не предлагаются. Исключения имеют отдельные live/test и реальные границы локального дня (23/25 часов при DST).

Не использовать сегодняшний снимок как принятую норму; backfill и время первого заказа не запускают прогрев 7/14/28 дней. Следующий этап и пробелы наблюдения — [аудит](../checkout-monitoring-audit.md), задача 12.B бэклога.

PostgreSQL-команда использует локальную тестовую базу, принятую `make backend-test-pgsql`; до теста она должна существовать. Для backend-тестов использовать PHP 8.4 по AGENTS.md. Выкладка и любые изменения production — отдельная команда владельца.
