# Ключи доступа сотрудников

Step 307; ADR 0034 и 0021; OWNER-PANEL §1, ADMIN-BACKEND §1, EXT-03.

После выкладки сотрудник входит обычным способом (пароль и MFA), открывает **Мой профиль → Ключи доступа**, указывает название устройства, текущий пароль и новый код MFA либо неиспользованный код восстановления. Кнопка «Добавить ключ доступа» запускает системное подтверждение. Можно добавить несколько ключей. На экране входа появится «Войти с Touch ID / Face ID»: конкретный способ подтверждения выбирает устройство — биометрия, PIN или аппаратный ключ с user verification. В браузере без WebAuthn остаётся вход по паролю и MFA.

Пароль и MFA сохраняются как резервный способ входа; подключённый MFA обязателен и для входа по ключу. Возвраты, права, настройки и остальные чувствительные действия сохраняют существующие проверки свежим MFA-кодом. Добавление и удаление своих ключей требуют текущий пароль и MFA/код восстановления независимо от способа входа. В списке видны только название и даты, чужие ключи недоступны.

При блокировке сотрудника, сбросе его MFA (через панель или серверную команду) и использовании ссылки восстановления пароля административные ключи удаляются. После восстановления доступа их нужно подключить заново. Обычная смена собственного пароля сохраняет ключи. Клиентские ключи эти операции не изменяют. Последний ключ можно удалить: резервные пароль и MFA остаются.

## Настройки и выкладка

Расширяющая миграция `2026_10_28_180000_create_platform_passkeys_table.php` создаёт только новую `platform_passkeys`; код предыдущего релиза продолжает работать. Миграция должна применяться до переключения на новый backend. Новых секретов и внешних сервисов не требуется.

Как и у клиентских passkeys, RP ID и разрешённый origin задаются установленным Laravel Passkeys из `APP_URL` (схема, хост и порт должны соответствовать реальному адресу браузера). В production обязателен HTTPS. Админка и кабинет сейчас расположены на одном origin; перенос админки на другой origin потребует отдельного решения для RP и повторного подключения ключей. Не менять `PASSKEYS_USER_HANDLE_SECRET`; если он не задан, используется `APP_KEY`, так что его ротация также требует учитывать существующие passkeys. Биометрические данные устройство серверу не передаёт.

Таблица, opaque user handle (`platform_staff|uuid`), маршруты, session challenge и cookies сотрудников отделены от клиентских. Для проверки challenge маршруты блокируют одновременную обработку одной сессии; cache store должен поддерживать atomic locks (production Redis, локальный database). Срок challenge/разрешения — 300 секунд; попытка завершения поглощает challenge и при ошибке. Проверяются origin, RP ID, user verification, подпись и счётчик. Аудит содержит события `staff.passkey_registered`, `staff.passkey_deleted`, `staff.passkey_login`, без содержимого credential, challenge или секретов. В карточке сотрудника последний вход учитывает оба способа.

## Проверки

`PlatformPasskeyTest` проверяет настоящие EC-подписи и none-attestation, одноразовость/срок challenge, обязательную MFA при подключении/отзыве, изоляцию guard и ключей, scope списка и удаления, origin/RP/UV/user handle/signature/counter, запрет заблокированному сотруднику и отзыв при восстановлении доступа. Запускать на SQLite и PostgreSQL 18 в Docker PHP 8.4.

`control/tests/passkeys.test.ts` и `passkeyApi.test.ts` проверяют интерфейс и отдельный platform CSRF. `control/tests/e2e/passkeys.mjs` проходит регистрацию через Chromium CDP virtual authenticator (resident key + UV), выход, вход по ключу, удаление и отказ удалённому ключу. Ему нужны **изолированный тестовый сотрудник**, `BW_CONTROL_URL`, `BW_EMAIL`, `BW_PASSWORD`, `BW_RECOVERY_CODES` (три одноразовых кода через запятую). Не использовать настоящую учётную запись: тест расходует коды восстановления. Опциональный `BW_SHOTS` сохраняет снимки профиля без пароля/кодов. Origin backend `APP_URL` должен совпадать с адресом тестовой админки. Реальный системный диалог Touch ID / Face ID проверяет владелец на своём устройстве после выкладки.
