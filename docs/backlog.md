- [x] **Читаемый аудит в админке.** Step 261: список и CSV показывают локализованное описание, имена объектов и ссылки по правам; сырой JSON, ID запроса и хэши убраны из отображения, а тест сверяет коды действий из бэкенда с переводами. Изменения выводятся как «было → стало»; старые записи без прежнего значения не получают выдуманного «было». Исходное требование:
  - у каждого действия — понятное название на ru/en/de; тест, что для каждого кода действия, который пишет бэкенд, есть перевод (без падения на сырой код); названия для 33 действий добавлены в Step 240, автоматическая сверка PHP-источников и набора динамических действий организации — Step 261;
  - у каждого действия — описание «что, кому, где, когда» из данных записи: например «Ответ на обращение SUP-… / №… отправлен на ivan@… (шаблон „Ответ“), 24 окт. 09:53» со ссылкой на обращение; «Запрошен доступ поддержки к магазину „…“ организации „…“, области: диагностика/материалы, срок 24 ч, обращение SUP-000001, причина: …» со ссылками на организацию и магазин; аналогично для остальных действий (пройти весь список);
  - названия организаций, магазинов, сотрудников, адреса — подставлять при показе по ID (с проверкой прав роли смотрящего), а не хранить лишние персональные данные в самой записи аудита; удалённый объект — «удалён», не пустота;
  - изменения показывать как «было → стало» с переведёнными значениями: «Статус обращения №… изменён: „Новое“ → „Закрыто“» (сейчас запись `{"status": "closed"}` без прежнего значения). Для этого бэкенд при любом изменении пишет в аудит прежнее и новое значение каждого изменённого поля; для старых записей без прежнего значения — «изменён на „Закрыто“», прежнее не выдумывать;
  - JSON в аудите не показывать нигде — ни в списке, ни в раскрытой записи (решение владельца 2026-10-24); каждое поле, нужное для понимания, превращается в часть текста. ID объекта и запроса, хэши — не выводить как набор символов (объект — ссылкой с названием);
  - то же в CSV-выгрузке аудита — колонка с читаемым описанием.

  - После подтверждения: уведомление на старый адрес «e-mail изменён», остальные сессии завершаются, аудит «было → стало».
  - Адрес занят другим аккаунтом — не раскрывать в интерфейсе (общее «проверьте почту»); ограничение частоты запросов.
  - **Paddle не трогаем** (решение владельца 2026-10-24): e-mail покупателя клиент сам вводит и меняет в Paddle; мы меняем адрес только у себя.
  - **Каналы уведомлений не меняются** (решение владельца 2026-10-24): e-mail-каналы — отдельные записи `notification_channels` со своим подтверждённым адресом; смена адреса входа их не трогает и не переносит.
  - API, `contracts/openapi.yaml`, тексты писем и экрана ru/en/de, тесты (каналы уведомлений не изменились; неверный пароль/код, истёкшая и чужая ссылка, отмена со старого адреса, занятый адрес, частота).
- [x] **Профиль сотрудника в админке («Сотрудники»).** (Step 268; решения владельца 2026-10-26: чужой пароль — только ссылкой на смену, дату рождения не собираем.) Изменение имени, фото, пароля и даты рождения. Кто кого может менять:
  - владелец сервиса (`platform_owner`) — любого сотрудника;
  - сотрудник с правом управления сотрудниками (`staff.manage`) — себя и других, кроме владельца сервиса;
  - сотрудник без этого права — только себя.
  Проверка прав на сервере при каждом изменении (не только скрытие кнопок), каждое изменение — в аудит в читаемом виде «было → стало» (для пароля и фото — только факт изменения, без значений).
  - **Фото:** JPG/PNG/WebP с ограничением размера, тип по содержимому, перекодирование без метаданных (как вложения формы обратной связи, Step 225), обрезка до квадрата; показ в списке сотрудников, в шапке и в аудите рядом с именем; удаление фото. Кнопка «Сделать селфи» рядом с выбором файла: камера браузера (`getUserMedia`, запрос разрешения), предпросмотр, «Снять» / «Переснять» / «Сохранить»; снимок уходит на сервер тем же путём, что и загруженный файл (та же проверка и перекодирование). Камера выключается сразу после снимка или отмены; нет камеры или доступ запрещён — понятное сообщение, остаётся загрузка файла. Работает только по HTTPS; учесть заголовок `Permissions-Policy` (camera для своего домена).
  - **Пароль:** свой — с вводом текущего пароля и кодом MFA, после смены завершаются остальные сессии. Чужой — решить с владельцем: предлагается не задавать пароль за другого, а отправить ему письмо со ссылкой на смену (одноразовая, с ограниченным сроком) с подтверждением действия кодом MFA; требования к паролю — как при входе.
  - **Дата рождения:** уточнить у владельца, зачем она нужна (поздравления, напоминания и т. п.) — это персональные данные, без цели не собирать; поле необязательное, видят только сам сотрудник и те, кто может его редактировать.
  - Тексты ru/en/de; тесты на матрицу прав (владелец / с правом / без права × себя / другого / владельца), на загрузку фото и смену пароля.

## Надёжность и безопасность: замечания PageSpeed

Добавлено владельцем 2026-10-27 по отчёту Google PageSpeed. Открытая задача: проработать защитные HTTP-заголовки публичного сайта и кабинетов. Указанная серьёзность — оценка отчёта, а не подтверждение найденной уязвимости.

- [ ] **CSP против XSS — высокая.** В отчёте не найдена политика `Content-Security-Policy` в принудительном режиме. Определить разрешённые источники и строгую политику; учесть встроенный CSS публичного сайта, скрипты, шрифты и Paddle. Проверить политику в режиме Report-Only, устранить нарушения и включить принудительное применение; для необходимых inline-блоков проработать nonce/hash.
- [ ] **Строгий HSTS — средняя.** Отчёт отмечает отсутствие `includeSubDomains` и `preload`. Проверить HTTPS на всех используемых поддоменах, включая почту и тестовые магазины; спланировать постепенное внедрение. Решение о `preload` и подаче в preload list принять отдельно после проверки готовности домена и последствий отката.
- [ ] **COOP — высокая.** Отчёт отмечает отсутствие `Cross-Origin-Opener-Policy`. Выбрать и проверить подходящую политику изоляции окна; проверить совместимость с оплатой, внешними окнами и входом в кабинеты.
- [ ] **Защита от кликджекинга — высокая.** В отчёте отсутствует правило управления встраиванием страниц. Настроить CSP `frame-ancestors` и при необходимости `X-Frame-Options`; проверить допустимые встраивания и предварительный просмотр страниц в редакторе.
- [ ] **Trusted Types против DOM XSS — высокая.** Отчёт отмечает отсутствие CSP `require-trusted-types-for`. Проверить DOM-приёмники, редактор HTML и зависимости Vue/Paddle; проработать политики Trusted Types, проверить нарушения и включить ограничения в поддерживающих браузерах.
- [ ] **Проверка результата.** Проверить заголовки на публичных страницах, `/app/`, `/owner/`, редиректах и ответах ошибок; пройти регистрацию, вход/MFA, редактор и оплату без реального списания. Повторить PageSpeed и сохранить результаты; добавить проверки выбранных заголовков. Связь: ТЗ §19, §31, §35.5 и security checklist в `spec/ACCEPTANCE.md`.

## 12. Мониторинг оформления заказа: настоящие покупатели, реалистичная синтетика, проверки DACH (владелец, 2026-10-29)

Владелец: текущая проверка «пришёл, кликнул, ушёл» слишком примитивна, реальных показателей не даёт и вряд ли продаётся. Задача — показывать владельцу магазина, где и сколько он теряет. Порядок: A (решения) → B (продажи против нормы, затем настоящие покупатели) → C (синтетика как активный зонд с профилями посетителей) → D (DACH). Принцип (владелец, 2026-10-30): универсальная проверка результата — покупок, а не охота на отдельные ошибки. Обход каталога отклонён владельцем как слишком дорогой. Измерение скорости (LCP/TTFB) в план не вошло — решить отдельно.

### A. Решения до кода (ADR, показать владельцу)

- [x] **Данные о покупателях (владелец, 2026-10-30): только обезличенные агрегаты.** Плагин / App считают на сервере магазина и раз в 5 минут отправляют только счётчики по шагам оформления (в корзину, оформление, попытки оплаты, заказы, ответы 5xx корзины/оформления), с разбивкой по грубым признакам (браузер, ОС, тип устройства, язык, часовой пояс, страна) только числами; группы меньше 5 за интервал — в «прочее». Никаких идентификаторов сеанса, IP и событий отдельного посетителя. Обещание прежнее: «данных о ваших покупателях не получаем — только статистику»; AVV и наши юридические документы не меняются. Точная воронка одного посетителя — сознательно не делаем (ADR 0090).
- [x] **Тарифы (владелец, 2026-10-29): в Start не входит** — требует заметных ресурсов. С Growth и выше; объёмы и частота по планам — при реализации, тексты тарифов и сайта — только после готовности.
- [x] **Оценка потерь по агрегатам (ADR 0090, уточнение модели 2026-10-30).** `потери ≈ (r₀ − r₁) × N × медиана оплаченного заказа`, где N — сумма счётчиков достижений рассматриваемого шага за интервал и сегмент, r₀ — обычное отношение числа заказов к счётчику шага в сопоставимых окнах магазина, r₁ — то же отношение за интервал инцидента. Это соотношения агрегатов, не вероятность завершения заказа конкретным посетителем: уникальные сеансы и индивидуальные корзины не передаются и не восстанавливаются. Для сигнала продаж без счётчиков шагов — оценка недостающих заказов относительно нормы × медиана оплаченного заказа. Медиана — по уже получаемым заказам за 28 дней, отдельно по валюте и live/test, minor units без float. Только оценка с диапазоном при достаточной выборке и статистически подтверждённом отклонении; не смешивается со сверкой денег. При неизвестном покрытии/норме/сумме оценка недоступна, а не равна нулю.
- [x] **Ступенчатый прогрев нормы (владелец, 2026-10-30; вместо «7 дней»).** < 7 дней — без тревог («собираем норму»); 7–13 — только «продажи остановились»; 14–27 — ещё «упали вдвое и больше» на протяжении нескольких часов (2–3 одинаковых дня недели + суточный профиль); ≥ 28 — полная чувствительность. Малые числа — расширять окно и статистическая проверка; дни инцидентов, акций и праздников (праздники DE = воскресенье, отметка «акция» в кабинете) не входят в норму; норма — скользящие 28 дней; пороги — подобрать на реальных данных до выпуска (ADR 0090).

Пропуски доставки не являются падением продаж.
- [ ] **Инциденты.** «С 14:00 отношение заказов к попыткам оплаты в мобильном Safari снизилось относительно нормы», «30% зарегистрированных попыток PayPal завершились отказом», «возросло число ответов корзины 500»: указать знаменатель счётчика, сегмент, шаг, интервал, покрытие и оценку потерь при наличии основания. ## 10. Контроль обработки оплаченных заказов

**Цель:** находить заказы, которые остановились на этапе, где по правилам магазина уже должно было произойти действие: оплата подтверждена, а обработка не началась; обработка начата и забыта; обещанная дата отправки прошла; отменённый оплаченный заказ без подтверждённого возврата. Позже — разрыв между статусом «отправлен» и данными службы доставки или склада. Пункты отмечать `[x]` с номером шага.

**Границы:** этапы A–D — контроль обработки **по данным магазина**, а не доказательство работы склада, передачи перевозчику или доставки; так это и называется в кабинете, письмах и тарифах. Независимое подтверждение появляется только в этапе E. Store-reported paid marker не доказывает capture: «оплаченный заказ» — это подтверждённое списание у провайдера с точной связью с заказом. Если провайдера нет или связь неоднозначна — «неизвестно», а не просрочка. Неизвестные и устаревшие данные не равны нулю и не дают просрочки. Деньги — только minor units. Запись во внешние системы не входит в план без отдельного ADR. Контур §43 `order_outcomes` не продаётся, пока заявленное покрытие не подтверждено (ADR 0066).

**Проверка кода (2026-10-23) — что есть и чего нет:**

| Нужно | Есть | Нет / дописать |
|---|---|---|
| Текущий статус заказа | `orders.status`, `source_updated_at` | — |

### A. Решения и модель (до кода)

- [ ] **Время перехода статуса.** По проверке выше точного времени смены статуса сейчас нет ни у одного коннектора. Дописать: плагин WooCommerce — время из хука `woocommerce_order_status_changed` (новое поле события, совместимо со старыми версиями плагина); WooCommerce REST API — проверить, можно ли читать системные заметки «Статус изменён» (`/orders/{id}/notes`) ключом «только чтение» и сколько это стоит запросов; Shopware — чтение `state_machine_history` по заказу с ограничением полей (какое право роли для этого нужно — проверить и добавить в инструкцию роли). Без точного времени — отсчёт по ревизии, в тексте интервал «между X и Y», спорная просрочка — «неизвестно». Время первого наблюдения не выдаётся за время действия.
- [ ] **Решения владельца → ADR.** Этапы и статусы по умолчанию для WooCommerce и Shopware («принят в обработку», «следующий этап», «отправлен», «завершён»); что не сбрасывает таймер (комментарий, телефон, адрес — учитывается только смена статуса); применимость (физический/виртуальный товар, предзаказ, ручная проверка, способы оплаты, исключения); сроки по умолчанию (пример «15 минут» не делать нормой); рабочие дни и часы, праздники (календарь федеральной земли или свой список); тариф; как связать с FIN-19 без дубля находок.
- [ ] **Модель ожидаемых действий.** Нет — новая таблица(ы). Версионированное правило магазина (этапы, переходы, сроки, календарь, исключения); ожидаемое действие по заказу: tenant/store/order, этап, версия правила и календаря, причина применимости, начало отсчёта с источником и точностью (`exact` / `between_revisions`), `due_at`, состояние `waiting / satisfied / overdue / unknown / exempted`, ссылки на доказательства (ревизии, платёж, возврат). Уникальный логический ключ против повторов и перестановки событий. Изменение правила не переписывает старые ожидания молча; пересчёт — отдельное действие с аудитом. Tenant scope везде.
- [ ] **Контракты.** Миграции, OpenAPI (правила, ожидания, список), event-контракт (время смены статуса, позже — дата отправки и отслеживание). Сверить с ТЗ §43 и дополнением 1.2 §§7–15, обновить ADR.

### B. Оплата подтверждена → заказ принят в обработку

- [ ] **Календарь сроков.** Нет — написать: расчёт `due_at` с рабочими днями и часами, часовым поясом магазина (есть), праздниками и cutoff; тесты на выходные, переход на летнее время, заказ после cutoff.
- [ ] **Правило и движок.** Начало отсчёта — подтверждённое списание с точной связью (есть); выполнено — переход в согласованный статус по времени из A; предзаказы и исключения — `exempted` с причиной. Устаревший источник (есть `ConnectorFreshness`) или неполные данные → `unknown`. Пересчёт по событиям проекции заказа и по расписанию.
- [ ] **Инцидент.** Новый тип в существующем движке: «Оплата заказа №1042 подтверждена. Заказ остаётся в статусе „Новый“, хотя срок передачи в обработку прошёл», один на ожидание; при позднем переходе закрывается сам с фактическим временем. Тексты ru/en/de, объяснение в карточке как в Step 232, уведомления без повторов.
- [ ] **Настройка в кабинете.** Нет — написать: включение, статусы (из встреченных у магазина), срок, календарь, исключения; предпросмотр «сколько текущих заказов попало бы в просрочку».
- [ ] **Проверка.** Тесты (повтор и перестановка событий, позднее подтверждение, отказ источника, комментарий/телефон без сброса таймера, tenant isolation), прогон на WooCommerce-Test и Shopware-Test.

### C. Следующие этапы обработки

- [ ] **Последовательность этапов.** Обработка начата → следующий согласованный статус; отправка отмечена → есть сведения об отправлении; заказ завершён → нет незакрытых противоречий по оплате или возврату (есть в сверке). Сроки отдельно по этапам; возврат на прежний статус и пропуск этапов — явно. Сведений об отправлении сейчас нет ни в одном коннекторе: Shopware — `order_delivery` (статус и `trackingCodes`, нужно право чтения и поля в запросе); WooCommerce — нет стандартного поля, только модули доставки (см. ниже).
- [ ] **Обещанная дата отправки.** Нет. Найти на реальных магазинах, где она хранится (поле модуля доставки, мета заказа), и сделать небольшой адаптер только для подтверждённого поля: «Заказ должен был быть отправлен 23 октября. По последним данным магазина отправка не отмечена». Если даты нет — правило магазина. Из текста карточки товара не выводить.
- [ ] **Отменённый оплаченный заказ без возврата.** Есть FIN-19 (инцидент «проверьте возврат» без суммы и срока). Дописать поверх него, а не рядом: возврат требуется по правилам этого заказа, сумма к возврату с учётом частичных возвратов и удержаний, срок обработки возврата, один инцидент с историей («Заказ отменён три рабочих дня назад. Возврат 89 € пока не подтверждён»). Отмена не всегда означает полный возврат.
- [ ] **Проверка.** Тесты по каждому этапу, прогон на тестовых магазинах.

### D. Список «Заказы, требующие действия»

- [ ] **Список в кабинете.** Нет — новый экран: заказ, что ожидается, просрочка (в рабочих часах/днях), основание; фильтры по магазину, этапу, ответственному. По клику — правило и версия, срок, доказательства, следующий шаг, история.
- [ ] **Ответственный и напоминание.** Ответственного нет — дописать (участник команды, с учётом ролей и скрытия сумм). Напоминание — на основе существующего snooze; отложить не значит признать устранённым: состояние остаётся «просрочено», пока действие не подтверждено данными.
- [ ] **Уведомления и сводка.** Есть ежедневная сводка (ADR 0067) — добавить просрочки; напоминания ответственному без повторов.

### E. Независимое подтверждение отправки (служба доставки или склад)

- [ ] **Выбор интеграции.** Нет. Одна реально используемая клиентами служба доставки или WMS (DACH: DHL, DPD, GLS, Sendcloud, Shipcloud и т. п.); проверить read-only API, права, идентификаторы, задержки, покрытие и связь отправления с заказом. Решение владельца → ADR.
- [ ] **Коннектор и этапы.** Различать: магазин поставил «Отправлен», создана этикетка, перевозчик принял посылку, посылка доставлена. Например: «Магазин отметил заказ отправленным. Этикетка создана, но приём перевозчиком не подтверждён в установленный срок». Отсутствие объекта — просрочка только после полного чтения нужного окна; недоступность API, неполная пагинация или неоднозначная связь — «неизвестно».
- [ ] **Проверка и запуск продажи.** Проверить на реальном магазине и реальной системе до заявления о независимом контроле; обновить acceptance, тарифы и тексты сайта; продавать `order_outcomes` только после подтверждения покрытия. Нагрузка, задержка, backfill и восстановление — в `docs/ops/`.

**Связь с требованиями:** ТЗ §12–14, §22–23, §29.1, §43; дополнение 1.2 §§7–15; ADR 0002, 0006, 0007, 0008, 0066, 0067; `docs/reconciliation-registry.md` FIN-19.

### H. Плагин WooCommerce: подключение прямо из WordPress (владелец, 2026-10-28)

**Проблема глазами клиента:** владелец как «простой клиент» поставил плагин из каталога WordPress.org и ждал результата — не понимая, что нужен аккаунт на нашем сайте. В 0.4.1 (Step 299) добавлены ссылки на регистрацию и уведомление на экране «Плагины», но это обычный текст, и клиенту всё равно приходится вручную копировать код подключения. Образец — блок WooCommerce/WordPress.com «Finish connecting your WordPress.com account» с кнопкой, ведущей на их сайт. Делать в два этапа, именно в этом порядке.

- [x] **Этап 1 — заметная карточка с кнопками (плагин 0.4.2).** (Step 305, плагин 0.4.2: карточка «Connect Business Watchdog» с кнопками «Connect to Business Watchdog», «Create a free account» и ссылкой «I have a connection code», скрытие для пользователя, на странице плагина — всегда.) Пока плагин не подключён и не остановлен — вместо текстового уведомления карточка в стиле админки WordPress: заголовок «Подключите Business Watchdog», одна строка, зачем нужен аккаунт, основная кнопка «Создать бесплатный аккаунт» (регистрация на языке админки) и вторая — «У меня есть код подключения» (страница плагина). Правила каталога WordPress.org (Guideline 11): только экран «Плагины» и своя страница, карточку можно закрыть (запоминать для пользователя, возвращать на странице плагина), без рекламы и без показа после подключения. Тексты через `__()`; интеграционные тесты: видна без подключения, не видна после подключения, остановки и закрытия. Выпуск по `docs/ops/integrations.md` (каталог + одобрение ZIP для кабинета).
- [x] **Этап 2 — подключение в один клик (ADR до кода).** (Step 305, ADR 0084, плагин 0.4.2; бэкенд выложен; живой проход на WooCommerce-Test — за владельцем после автообновления плагина до 0.4.2.) Кнопка «Подключить к Business Watchdog» на странице плагина открывает наш сайт; клиент регистрируется или входит, выбирает или создаёт магазин (адрес берётся с сайта WordPress); сервис возвращает его в админку WordPress, и плагин подключается сам — без копирования кода. Решить в ADR: одноразовый `state` с коротким сроком и защитой от повтора; адрес возврата — только админка того же сайта (`admin_url`), домен должен совпадать с адресом магазина в кабинете (иначе — понятная ошибка и ручной путь); код подключения не попадает в историю браузера и логи (передача через POST или обмен короткого кода на сервере); права пользователя WordPress (`manage_woocommerce`) и nonce на обеих сторонах; что делать, если магазин уже подключён другим способом (REST API) — один источник заказов на магазин; аудит. Ручной путь с кодом остаётся. Тесты сервиса и плагина, живая проверка на WooCommerce-Test.
- [x] **Повторное подключение после «Disconnect» в WordPress (владелец, 2026-10-30).** Обмен кода заменяет подключение, которое клиент отключил только в WordPress, вместо ошибки `pairing_failed` (Step 321, только сервис; не выложено).
- [ ] **«Disconnect» в плагине сообщает сервису (владелец, 2026-10-30).** Сейчас кнопка стирает подключение только в WordPress; у нас интеграция остаётся активной и просто замолкает. Следующая версия плагина: по «Disconnect» подписанный ключом подключения запрос в сервис (новый endpoint), сервис отзывает интеграцию и её ключи с причиной «отключено в WordPress» (аудит), кабинет показывает это у магазина и на экране «Плагины» с кнопкой «Подключить снова». Если сервис недоступен — плагин всё равно отключается локально, а сервис увидит отзыв при повторном подключении (Step 321). То же для удаления плагина (uninstall) — по возможности. Контракт OpenAPI, тесты плагина и сервиса, выпуск плагина — выгрузка в SVN только по команде владельца.

**Связь:** Step 299 (0.4.1), Step 285 (одобрение ZIP), ADR 0077 (API-first), правила каталога WordPress.org.


### I. Аналитика воронки подключения из плагина (владелец, 2026-10-28)

- [x] **Измерять путь от интереса к активации интеграции** (Step 305, ADR 0084: пять этапов, отчёт в «Обзоре» админки за период и по месту нажатия), чтобы следующая партия загрузок плагина показывала больше, чем число скачиваний. Собирать следующие события и показывать в админке количество и конверсию между этапами за выбранный период/по источнику:

| Событие | Что покажет |
|---|---|
| Нажатие регистрации из плагина | Пользователь заинтересовался |
| Открытие формы регистрации | Дошёл до сайта |
| Успешная регистрация | Создал аккаунт |
| Создание кода подключения | Решил подключить магазин |
| Успешное соединение | Активировал интеграцию |

- [x] **UTM-метки в ссылках плагина.** (Step 305: ссылки плагина ведут на `/go/wordpress-plugin`, который считает нажатие и открывает `/{язык}/signup?utm_source=wordpress_plugin&utm_medium=onboarding&utm_content=<место>`; кнопка подключения — `/connect/woocommerce`; путь хранится только в сессии сервера.) Например, `https://business-watchdog.com/en/signup?utm_source=wordpress_plugin&utm_medium=onboarding` (действующий адрес регистрации — `/{locale}/signup`; `/en/register` из примера владельца заменить на него). Сохранять источник между этапами; учитывать ru/en/de. Отличать факт нажатия от открытия формы: одна UTM-метка сама по себе не доказывает нажатие. Определить минимальный способ регистрации события без фоновой телеметрии плагина.
- [x] **Достоверность событий.** (Step 305: аккаунт, код и подключение — по действию сервера, один раз на организацию и магазин; в один клик код создаётся при «Подключить».) Успешную регистрацию, создание кода и соединение фиксировать по подтверждённому действию сервера; повторные запросы не должны завышать конверсию. Создание кода не считать соединением. Учесть ручной путь и будущее подключение в один клик (раздел H), где создание кода может не быть отдельным действием клиента.
- [x] **Минимум данных.** (Step 305: без IP, браузера, адресов, кодов и данных покупателей; хранение 13 месяцев; удаление магазина или организации удаляет события.) Не отправлять в аналитику данные покупателей, содержимое заказов, пароли, API-ключи, секреты интеграций и сами коды подключения. Хранить только необходимые события и разрешённые метки источника; не сохранять произвольные query-параметры или полный URL, где могут оказаться секреты. До реализации определить сроки хранения и способ связывания этапов с учётом приватности и правил WordPress.org.
- [ ] **Проверка.** (Автотесты сервиса, кабинета, админки и плагина — Step 305; живой проход на WooCommerce-Test — за владельцем после автообновления плагина до 0.4.2; бэкенд уже выложен.) Пройти путь из плагина до соединения, проверить атрибуцию источника, повторы, переходы между языками и отсутствие запрещённых данных в событиях и логах; доступ к отчёту — только сотрудникам с соответствующим правом. Связь: раздел H, Step 299, ТЗ §31 и требования к защите секретов; это воронка подключения к SaaS, отдельно от наблюдения за checkout покупателей.
