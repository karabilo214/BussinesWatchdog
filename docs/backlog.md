## Доступ и интерфейс

- [ ] MFA: passkeys/WebAuthn, «доверенное устройство», список сессий с «выйти везде», принудительная MFA для всей команды (ADR 0021).
- [ ] Редактор страниц: перетаскивание блоков (ADR 0045).
- [ ] «Сервис»: действия из админки (например, повтор «мёртвых» записей) с подтверждением кодом и аудитом (ADR 0051).
- [ ] **Счётчики (badge) в меню админки.** У пунктов, где что-то ждёт внимания, — значок с количеством, например «Обращения 3» при новых обращениях. Пройти все пункты меню и решить по каждому; кандидаты: «Обращения» (новые/неотвеченные), «Оплаты» (возвраты, ждущие одобрения владельца), «Подписки» (просроченная оплата, ждут действия), «Сервис» (число проблем или цвет состояния warn/crit вместо числа), «Организации» (запросы доступа поддержки в ожидании). Что считается «новым» — по состоянию записи на сервере (не «непрочитано» у каждого сотрудника), если владелец не решит иначе. Числа — одним лёгким запросом на сервер с периодическим обновлением, только по разделам, на которые у роли сотрудника есть право; без данных клиентов в ответе. Тексты ru/en/de, тесты на права и подсчёт.
- [ ] **Читаемый аудит в админке.** Сейчас запись показывает тип и ID объекта, ID запроса и сырой JSON (`reply_id`, `template`, `content_hash`), а у части действий нет перевода названия — `AuditView` при отсутствии `audit_action.<код>` выводит сам код (пример: `support_grant.requested`, у самой записи только «Причина: test request» и «BW»). Нужно, чтобы запись читалась человеком:
  - у каждого действия — понятное название на ru/en/de; тест, что для каждого кода действия, который пишет бэкенд, есть перевод (без падения на сырой код);
  - у каждого действия — описание «что, кому, где, когда» из данных записи: например «Ответ на обращение SUP-… / №… отправлен на ivan@… (шаблон „Ответ“), 24 окт. 09:53» со ссылкой на обращение; «Запрошен доступ поддержки к магазину „…“ организации „…“, области: диагностика/материалы, срок 24 ч, обращение SUP-000001, причина: …» со ссылками на организацию и магазин; аналогично для остальных действий (пройти весь список);
  - названия организаций, магазинов, сотрудников, адреса — подставлять при показе по ID (с проверкой прав роли смотрящего), а не хранить лишние персональные данные в самой записи аудита; удалённый объект — «удалён», не пустота;
  - изменения показывать как «было → стало» с переведёнными значениями: «Статус обращения №… изменён: „Новое“ → „Закрыто“» (сейчас запись `{"status": "closed"}` без прежнего значения). Для этого бэкенд при любом изменении пишет в аудит прежнее и новое значение каждого изменённого поля; для старых записей без прежнего значения — «изменён на „Закрыто“», прежнее не выдумывать;
  - JSON в аудите не показывать нигде — ни в списке, ни в раскрытой записи (решение владельца 2026-10-24); каждое поле, нужное для понимания, превращается в часть текста. ID объекта и запроса, хэши — не выводить как набор символов (объект — ссылкой с названием);
  - то же в CSV-выгрузке аудита — колонка с читаемым описанием.
- [ ] **Профиль сотрудника в админке («Сотрудники»).** Изменение имени, фото, пароля и даты рождения. Кто кого может менять:
  - владелец сервиса (`platform_owner`) — любого сотрудника;
  - сотрудник с правом управления сотрудниками (`staff.manage`) — себя и других, кроме владельца сервиса;
  - сотрудник без этого права — только себя.
  Проверка прав на сервере при каждом изменении (не только скрытие кнопок), каждое изменение — в аудит в читаемом виде «было → стало» (для пароля и фото — только факт изменения, без значений).
  - **Фото:** JPG/PNG/WebP с ограничением размера, тип по содержимому, перекодирование без метаданных (как вложения формы обратной связи, Step 225), обрезка до квадрата; показ в списке сотрудников, в шапке и в аудите рядом с именем; удаление фото. Кнопка «Сделать селфи» рядом с выбором файла: камера браузера (`getUserMedia`, запрос разрешения), предпросмотр, «Снять» / «Переснять» / «Сохранить»; снимок уходит на сервер тем же путём, что и загруженный файл (та же проверка и перекодирование). Камера выключается сразу после снимка или отмены; нет камеры или доступ запрещён — понятное сообщение, остаётся загрузка файла. Работает только по HTTPS; учесть заголовок `Permissions-Policy` (camera для своего домена).
  - **Пароль:** свой — с вводом текущего пароля и кодом MFA, после смены завершаются остальные сессии. Чужой — решить с владельцем: предлагается не задавать пароль за другого, а отправить ему письмо со ссылкой на смену (одноразовая, с ограниченным сроком) с подтверждением действия кодом MFA; требования к паролю — как при входе.
  - **Дата рождения:** уточнить у владельца, зачем она нужна (поздравления, напоминания и т. п.) — это персональные данные, без цели не собирать; поле необязательное, видят только сам сотрудник и те, кто может его редактировать.
  - Тексты ru/en/de; тесты на матрицу прав (владелец / с правом / без права × себя / другого / владельца), на загрузку фото и смену пароля.

## Админка: карточка клиента («Клиенты»)

Каждое действие ниже — проверка прав на сервере, обязательная причина, запись в аудит в читаемом виде (см. «Читаемый аудит в админке»), тексты ru/en/de, тесты на права.

- [ ] **«Обзор» → блок «Действия»: «Отключить MFA».** Только владелец сервиса (`platform_owner`), с кодом из его приложения-аутентификатора. Выбор участника организации (по умолчанию владелец организации). Сброс уже есть в API — `POST /platform-api/v1/tenants/{tenant}/members/{user}/mfa/reset` (право `CUSTOMER_MFA_RESET`, код и причина) — переиспользовать; сузить право до владельца сервиса (сейчас право может быть и у других ролей — проверить и решить). Клиенту — письмо о сбросе MFA.
- [ ] **«Обзор» → блок «Действия»: «Отправить ссылку на восстановление пароля».** Владелец сервиса и сотрудник с правом (какое право — решить: новое или существующее право поддержки). Отправляется стандартное письмо восстановления пароля на адрес участника, пароль сотрудник не видит и не задаёт; ограничение частоты; в аудите — кому и когда отправлено.
- [ ] **«Магазины» → «Редактировать».** Пока меняется только название (потом — другие параметры). Доступно сотруднику только при действующем доступе поддержки от владельца организации к этому магазину — для этого нужна новая область доступа (например, «изменение настроек магазина») в запросе доступа (ADR 0078), проверка grant на сервере при сохранении; в аудите «было → стало», владельцу организации — видно в журнале доступа поддержки.
- [ ] **«Доступ поддержки» → «История».**
  - «Отправить повторно» — для любой записи, включая отозванные, отклонённые и истёкшие: создаёт новый запрос с теми же магазином, областями, сроком и основанием (новый номер SUP-…, прежний запрос не оживает) и отправляет письмо владельцу организации; если такой же запрос уже ждёт — повтор письма по нему, без дубля (как сейчас).
  - «Отменить» — для запросов, ждущих одобрения: запрос закрывается, ссылка из письма перестаёт работать, владельцу организации запрос больше не показывается как ожидающий.
  - «Удалить» — для любой записи истории: реального удаления нет, запись скрывается из списка (отметка «скрыто» с кем и когда), в аудите и журнале у владельца организации остаётся; действующий доступ «удалением» не отзывается — сначала отзыв.
- [ ] **«Аудит» в карточке клиента** — то же, что «Читаемый аудит в админке»: понятные сообщения на языке сотрудника, «было → стало», без JSON.
- [ ] **Кабинет клиента `/app/settings/support` → «История»** — то же самое для владельца организации: у каждого события переведённое название на ru/en/de (без сырых кодов вроде `support_grant.requested`; тест на покрытие всех кодов), понятный текст «кто, что, к какому магазину, когда»: «Сотрудник поддержки Volodymyr запросил доступ к магазину „…“ (диагностика, материалы) на 24 ч, обращение SUP-000001, причина: …», «Вы одобрили…», «Сотрудник открыл материалы проверки…», «Доступ истёк / отозван»; без JSON, ID и хэшей. Имя сотрудника показывать так, как решено в ADR 0078 (не раскрывать лишнего).

## 10. Контроль обработки оплаченных заказов

**Цель:** находить заказы, которые остановились на этапе, где по правилам магазина уже должно было произойти действие: оплата подтверждена, а обработка не началась; обработка начата и забыта; обещанная дата отправки прошла; отменённый оплаченный заказ без подтверждённого возврата. Позже — разрыв между статусом «отправлен» и данными службы доставки или склада. Пункты отмечать `[x]` с номером шага.

**Границы:** этапы A–D — контроль обработки **по данным магазина**, а не доказательство работы склада, передачи перевозчику или доставки; так это и называется в кабинете, письмах и тарифах. Независимое подтверждение появляется только в этапе E. Store-reported paid marker не доказывает capture: «оплаченный заказ» — это подтверждённое списание у провайдера с точной связью с заказом. Если провайдера нет или связь неоднозначна — «неизвестно», а не просрочка. Неизвестные и устаревшие данные не равны нулю и не дают просрочки. Деньги — только minor units. Запись во внешние системы не входит в план без отдельного ADR. Контур §43 `order_outcomes` не продаётся, пока заявленное покрытие не подтверждено (ADR 0066).

**Проверка кода (2026-10-23) — что есть и чего нет:**

| Нужно | Есть | Нет / дописать |
|---|---|---|
| Текущий статус заказа | `orders.status`, `source_updated_at` | — |
| История статусов | `order_revisions`: снимок каждой ревизии источника + `observed_at` | Ни один коннектор не передаёт **время смены статуса**. Плагин отправляет `source_updated_at` = `date_modified` заказа (меняется и от комментария, и от правки телефона); REST API WooCommerce заметки заказа не читает; Shopware `state_machine_history` не читает. Сейчас время перехода известно только как «между двумя ревизиями» |
| Подтверждённая оплата со связью | платежи провайдеров, точная связь с заказом, FIN-01…24 | — |
| Отмена оплаченного заказа | FIN-19 `MONEY_CANCELLED_PAID`: инцидент «внимание», «проверьте возврат», без суммы и без срока | Срока обработки возврата, «возврат требуется по правилам заказа», суммы к возврату и одной истории по инциденту нет |

### A. Решения и модель (до кода)

- [ ] **Время перехода статуса.** По проверке выше точного времени смены статуса сейчас нет ни у одного коннектора. Дописать: плагин WooCommerce — время из хука `woocommerce_order_status_changed` (новое поле события, совместимо со старыми версиями плагина); WooCommerce REST API — проверить, можно ли читать системные заметки «Статус изменён» (`/orders/{id}/notes`) ключом «только чтение» и сколько это стоит запросов; Shopware — чтение `state_machine_history` по заказу с ограничением полей (какое право роли для этого нужно — проверить и добавить в инструкцию роли). Без точного времени — отсчёт по ревизии, в тексте интервал «между X и Y», спорная просрочка — «неизвестно». Время первого наблюдения не выдаётся за время действия.
- [ ] **Решения владельца → ADR.** Этапы и статусы по умолчанию для WooCommerce и Shopware («принят в обработку», «следующий этап», «отправлен», «завершён»); что не сбрасывает таймер (комментарий, телефон, адрес — учитывается только смена статуса); применимость (физический/виртуальный товар, предзаказ, ручная проверка, способы оплаты, исключения); сроки по умолчанию (пример «15 минут» не делать нормой); рабочие дни и часы, праздники (календарь федеральной земли или свой список); тариф; как связать с FIN-19 без дубля находок.
- [ ] **Модель ожидаемых действий.** Нет — новая таблица(ы). Версионированное правило магазина (этапы, переходы, сроки, календарь, исключения); ожидаемое действие по заказу: tenant/store/order, этап, версия правила и календаря, причина применимости, начало отсчёта с источником и точностью (`exact` / `between_revisions`), `due_at`, состояние `waiting / satisfied / overdue / unknown / exempted`, ссылки на доказательства (ревизии, платёж, возврат). Уникальный логический ключ против повторов и перестановки событий. Изменение правила не переписывает старые ожидания молча; пересчёт — отдельное действие с аудитом. Tenant scope везде.
- [ ] **Контракты.** Миграции, OpenAPI (правила, ожидания, список), event-контракт (время смены статуса, позже — дата отправки и отслеживание). Сверить с ТЗ §43 и дополнением 1.2 §§7–15, обновить ADR.

### B. Оплата подтверждена → заказ принят в обработку

- [ ] **Календарь сроков.** Нет — написать: расчёт `due_at` с рабочими днями и часами, часовым поясом магазина (есть), праздниками и cutoff; тесты на выходные, переход на летнее время, заказ после cutoff.
- [ ] **Правило и движок.** Начало отсчёта — подтверждённое списание с точной связью (есть); выполнено — переход в согласованный статус по времени из A; предзаказы и исключения — `exempted` с причиной. Устаревший источник (есть `ConnectorFreshness`) или неполные данные → `unknown`. Пересчёт по событиям проекции заказа и по расписанию.
- [ ] **Инцидент.** Новый тип в существующем движке: «Оплата заказа №1042 подтверждена. Заказ остаётся в статусе „Новый“, хотя срок передачи в обработку прошёл», один на ожидание; при позднем переходе закрывается сам с фактическим временем. Тексты ru/en/de, объяснение в карточке как в Step 232, уведомления без повторов.
- [ ] **Настройка в кабинете.** Нет — написать: включение, статусы (из встреченных у магазина), срок, календарь, исключения; предпросмотр «сколько текущих заказов попало бы в просрочку».
- [ ] **Проверка.** Тесты (повтор и перестановка событий, позднее подтверждение, отказ источника, комментарий/телефон без сброса таймера, tenant isolation), прогон на WooCommerce-Test и Shopware-Test.

### C. Следующие этапы обработки

- [ ] **Последовательность этапов.** Обработка начата → следующий согласованный статус; отправка отмечена → есть сведения об отправлении; заказ завершён → нет незакрытых противоречий по оплате или возврату (есть в сверке). Сроки отдельно по этапам; возврат на прежний статус и пропуск этапов — явно. Сведений об отправлении сейчас нет ни в одном коннекторе: Shopware — `order_delivery` (статус и `trackingCodes`, нужно право чтения и поля в запросе); WooCommerce — нет стандартного поля, только модули доставки (см. ниже).
- [ ] **Обещанная дата отправки.** Нет. Найти на реальных магазинах, где она хранится (поле модуля доставки, мета заказа), и сделать небольшой адаптер только для подтверждённого поля: «Заказ должен был быть отправлен 23 октября. По последним данным магазина отправка не отмечена». Если даты нет — правило магазина. Из текста карточки товара не выводить.
- [ ] **Отменённый оплаченный заказ без возврата.** Есть FIN-19 (инцидент «проверьте возврат» без суммы и срока). Дописать поверх него, а не рядом: возврат требуется по правилам этого заказа, сумма к возврату с учётом частичных возвратов и удержаний, срок обработки возврата, один инцидент с историей («Заказ отменён три рабочих дня назад. Возврат 89 € пока не подтверждён»). Отмена не всегда означает полный возврат.
- [ ] **Проверка.** Тесты по каждому этапу, прогон на тестовых магазинах.

### D. Список «Заказы, требующие действия»

- [ ] **Список в кабинете.** Нет — новый экран: заказ, что ожидается, просрочка (в рабочих часах/днях), основание; фильтры по магазину, этапу, ответственному. По клику — правило и версия, срок, доказательства, следующий шаг, история.
- [ ] **Ответственный и напоминание.** Ответственного нет — дописать (участник команды, с учётом ролей и скрытия сумм). Напоминание — на основе существующего snooze; отложить не значит признать устранённым: состояние остаётся «просрочено», пока действие не подтверждено данными.
- [ ] **Уведомления и сводка.** Есть ежедневная сводка (ADR 0067) — добавить просрочки; напоминания ответственному без повторов.

### E. Независимое подтверждение отправки (служба доставки или склад)

- [ ] **Выбор интеграции.** Нет. Одна реально используемая клиентами служба доставки или WMS (DACH: DHL, DPD, GLS, Sendcloud, Shipcloud и т. п.); проверить read-only API, права, идентификаторы, задержки, покрытие и связь отправления с заказом. Решение владельца → ADR.
- [ ] **Коннектор и этапы.** Различать: магазин поставил «Отправлен», создана этикетка, перевозчик принял посылку, посылка доставлена. Например: «Магазин отметил заказ отправленным. Этикетка создана, но приём перевозчиком не подтверждён в установленный срок». Отсутствие объекта — просрочка только после полного чтения нужного окна; недоступность API, неполная пагинация или неоднозначная связь — «неизвестно».
- [ ] **Проверка и запуск продажи.** Проверить на реальном магазине и реальной системе до заявления о независимом контроле; обновить acceptance, тарифы и тексты сайта; продавать `order_outcomes` только после подтверждения покрытия. Нагрузка, задержка, backfill и восстановление — в `docs/ops/`.

**Связь с требованиями:** ТЗ §12–14, §22–23, §29.1, §43; дополнение 1.2 §§7–15; ADR 0002, 0006, 0007, 0008, 0066, 0067; `docs/reconciliation-registry.md` FIN-19.

## 11. Подключение магазина «за руку»

**Цель:** клиент подключает магазин без выбора технического способа и без переписки с поддержкой: выбирает платформу, получает точные шаги для своей системы, при ошибке видит причину и способ исправления, а в конце — доказательство, что данные действительно идут. Задача в основном про интерфейс и тексты; путь по ключу «только чтение» (API-first, ADR 0077) последовательно становится основным везде. Пункты отмечать `[x]` с номером шага.

**Границы:** в текстах — только обещания, подтверждённые реализацией. Неполное покрытие остаётся явно видимым, без преждевременного зелёного «всё работает». Тексты ru/en/de.

### B. Платформа вместо технического способа

- [x] **Сначала платформа (Step 237) — так, чтобы ошибиться было почти невозможно.** Отдельный первый шаг до остальных полей: крупные карточки с логотипом и названием платформы, **ничего не выбрано по умолчанию**, без выбора дальше не пройти; сервер требует платформу явно (`required` в `CreateStoreRequest`). Затем адрес магазина и определение по нему (признаки страницы без входа, как в публичной проверке магазина): совпало — «Похоже, это Shopware» с подтверждением; не совпало с выбранным — явное предупреждение «Вы выбрали WooCommerce, а по адресу похоже на Shopware» с выбором; не определилось — оставить выбор клиента. Платформа видна в шапке магазина и на всех экранах подключения (логотип + название), инструкции другой платформы не показываются.
- [x] **Исправление ошибки (Step 237) без пересоздания.** Сменить платформу у магазина, пока к нему не подключён ни один источник заказов (иначе — сначала отключить источник; заказы и находки разных платформ не смешиваются). Действие в настройках магазина с подтверждением и записью в аудит; при ошибке подключения из-за платформы (ключ Shopware в магазине WooCommerce, Admin API `/api` отвечает у «WooCommerce»-магазина и наоборот) — текст «Похоже, магазин на другой платформе» с кнопкой смены.
- [x] **Основной путь (Step 237) и дополнительный.** Переделать `OrderSource` и способ подключения в `ShopwarePanel`: основной вариант — «Подключить WooCommerce (Shopware) через API: установка не требуется, сервис получает доступ к данным для наблюдения»; плагин/App — отдельным блоком ниже «Дополнительное наблюдение за оформлением заказа, требуется установка коннектора» с перечнем того, что он добавляет (наблюдение за оформлением, мгновенные изменения, тест/боевой режим Stripe для WooCommerce). Убрать вкладки как равноценный технический выбор; переход с плагина на API сохранить.

### G. Подтверждение работы вебхука после настройки (замечание владельца после Step 237)

**Проблема глазами клиента:** после создания вебхуков в WooCommerce кабинет никак не сообщает, сделано ли всё правильно и работают ли они. Клиенту нужен понятный результат именно его действия в магазине, а не только список полей для копирования или сохранённый секрет. Тот же принцип применить к настройке вебхуков Stripe и PayPal.

- [ ] **Дать проверяемое подтверждение.** После настройки вебхука в WooCommerce клиент может безопасно проверить доставку без реальной покупки и увидеть в кабинете результат: «событие от WooCommerce получено и проверено» с временем. Продумать контрольное событие/проверку с реального WooCommerce-Test; запрос, отправленный самим нашим сервером напрямую в свой endpoint, не доказывает работу доставки из магазина. Для Stripe/PayPal — аналогичное подтверждение после настройки у провайдера.
- [ ] **Показать понятные этапы и исправление.** В блоке каждого вебхука различать: «инструкция/секрет подготовлены», «ожидаем проверку доставки», «работает: получено подтверждённое событие», «проверка не прошла» с конкретной причиной и следующим шагом. Обновлять экран после проверки без ручного поиска статуса. Сохранение секрета или Webhook ID не помечать зелёным успехом. При отсутствии обычных заказов не объявлять вебхук сломанным только из-за тишины.
- [ ] **Объяснить эффект и проверить путь.** Рядом с результатом коротко показать, что уже работает через плановую синхронизацию и что ускоряет вебхук. Пройти создание и контрольную доставку на WooCommerce-Test, затем доступные тестовые Stripe/PayPal; проверить ошибки, тексты ru/en/de и единый стиль окон. Автотестами закрепить переходы между этапами и запрет ложного «работает» до события от внешней системы.
