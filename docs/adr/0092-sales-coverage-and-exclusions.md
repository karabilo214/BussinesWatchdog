# ADR 0092: Покрытие созданных заказов и исключения перед нормой продаж

Дата: 2026-10-30. Статус: реализация следующего среза задачи 12.B по ADR 0090/0091. Статистические пороги, тарифы и юридические документы не меняет.

## Что считается подтверждением

Покрытие метрики созданных заказов подтверждается только полным чтением диапазона `created_at` через поддерживаемый API магазина, после завершения пагинации и обработки нормализованных снимков/удалений. WooCommerce использует существующие recent/audit, Shopware — audit. Delta-watermark, heartbeat, успешная HTTP-страница и число уже найденных заказов сами по себе подтверждением не являются. Пропуски mapper, исчерпание бюджета и неполная проверка удалений не дают нового покрытия.

Подтверждённая граница заканчивается временем начала чтения, не временем окончания HTTP-запросов. Для WooCommerce запрос `after` начинается на секунду раньше границы доказательства: REST API с `dates_are_gmt=true` использует date query, где `after` может быть строгим. Это не расширяет заявленное покрытие и не теряет заказ ровно на нижней границе. Shopware использует `createdAt >= from`. Чтение подтверждает текущее поддерживаемое представление магазина, а не неизменяемую бухгалтерскую историю всех удалённых заказов.

Даже полная выдача API сначала ждёт inbox. Любой неприменённый order snapshot/deletion, включая quarantine/dead-letter, блокирует подтверждение. Дополнительно проверяются `provider_object_states`: для увиденного заказа должна существовать проекция не старее нормализованной ревизии. Это защищает от случая, когда приём отклонил событие без inbox-строки, а emitter сохранил состояние объекта. Существующий emitter этим срезом не переписывается.

В отчёте отдельны `metric_coverage.orders_created`, `store_paid_markers` и `orders_with_capture`. Только первое может стать complete. Полнота независимых списаний и исторических paid-маркеров из списка заказов не следует. Общая норма остаётся unknown, тревоги выключены; `baseline_eligible` означает пригодность данного часа как кандидата истории созданных заказов, а не принятый baseline, готовую статистику конверсии или гарантию продаж.

## Хранение и совместимость выпуска

Журнал v1 — новое nullable JSONB-поле `integrations.sales_coverage`: время первого фактического наблюдения, последний результат полного/частичного чтения, не более одного ожидающего чтения на recent/audit и объединение доказанных UTC-интервалов в последних 28 сутках. При повторных/переставленных чтениях покрытие не увеличивается счётчиком, интервалы объединяются только без разрыва. Начало исторического backfill не выдаётся за начало наблюдения; прогрев 7/14/28 этим срезом ещё не вычисляется.

Исключения — nullable JSONB `stores.sales_baseline_exclusions`: по локальной дате, виду и live/test, с сохранёнными UTC-границами и часовым поясом. Размер ограничен горизонтом истории: принимаются только прошедшие 28 локальных дней и текущий день, фиксированный перечень причин и два режима. Никакого текста покупателя, сеанса или события посетителя здесь нет. Оба поля удаляются вместе с существующими строками магазина/интеграции.

Новые таблицы со `store_id` на этом шаге намеренно не создаются: предыдущая версия `StoreDeletion` блокирует неизвестные store-owned таблицы. Nullable-поля сохраняют работоспособность старого кода во время expand/contract rollout и его отката. Удаление организации продолжает пользоваться теми же таблицами и порядком; не требуется обходить защиту полноты purge. Миграция только добавляет поля, не меняет прежние данные.

## Исключения и автоматизация

Дни с инцидентами исключаются в часовом поясе магазина целиком: от first_bad_at (или created_at, если начало неизвестно) до resolved_at, по соответствующему режиму; null-mode incident рассматривается консервативно для обоих режимов. Текущие паузы магазина, capacity, организации и оплаченного доступа исключают кандидат истории; плановый сборщик сохраняет отметку pause текущего локального дня для live/test, чтобы она осталась после возобновления.

Доменный метод `excludeDay` поддерживает promotion/holiday/pause/data_gap. Это слой хранения, не пользовательская настройка: customer API/кнопки пометок и календарь праздников DE ещё предстоит реализовать. Прошлые непомеченные паузы не восстанавливаются по сегодняшнему состоянию. Возобновление и backfill не заменяют журнал исключений, а позднее исправление даты инцидента учитывается при следующем чтении отчёта.

`sales:finalize-coverage` — техническое задание scheduler раз в минуту с leader lock и запретом перекрытия; оно дождётся проекций, объединит интервалы, удалит старые интервалы/пометки и сохранит текущие дни паузы. Между tenant выбираются только ID; обработка идёт в TenantContext с tenant/store predicates и блокировкой изменяемой строки. От владельца новых ручных серверных команд не требуется. Плагин WooCommerce пока не даёт доказательства покрытия таким способом; для него остаётся unknown до соответствующего контракта агрегатов.

Уточнение Step 325 / [ADR 0093](0093-sales-warmup-eligible-local-days.md): технический журнал хранит 28 завершённых локальных дней плюс текущую часть дня; диагностические ступени созданных заказов теперь вычисляются отдельно от готовности нормы и тревог.
