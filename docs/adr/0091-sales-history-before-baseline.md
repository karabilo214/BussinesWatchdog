# ADR 0091: Наблюдаемая история продаж перед расчётом нормы

Дата: 2026-10-30. Статус: первый диагностический срез задачи 12.B, в рамках принятых решений ADR 0090; пороги тревог не устанавливает.

## Решение

Перед детектором «продажи остановились / упали» добавляется внутренняя команда `sales:history` и tenant-scoped сервис чтения существующих проекций за интервал не более 28 суток. Они не вызывают внешние системы, не создают уведомления, не меняют данные и не включают новую функцию в тарифы.

Разделяются три наблюдения:

- `orders_created_observed` — заказы по времени создания источника, не поступления в наш inbox;
- `store_paid_markers_observed` — отметки оплаты магазина по `paid_marked_at`, без утверждения независимого списания;
- `orders_with_capture_observed` — число заказов с положительной действующей allocation и положительным succeeded capture независимого провайдера, в интервале первого capture. Это не число финансовых операций и не доказательство полной оплаты суммы заказа. Несколько captures одного заказа не увеличивают показатель; refund/fee/authorization не являются capture.

У одного магазина после переподключения могут оставаться несколько проекций одного внешнего заказа. Для счётчиков берётся последняя проекция по source_updated_at, updated_at, id; удаление, synthetic и mode проверяются после выбора. Положительные подтверждения старых allocations сохраняют значение и при смене источника заказа: связываются только внутри того же tenant/store и внешнего ID заказа. Режим и валюта связей обязаны совпадать. Непривязанные и отнесённые к чужому магазину платежи не доказывают продажи этого магазина.

Почасовые корзины ключуются UTC, локальная метка содержит смещение и день недели магазина; повторный час при DST не сливается. Границы `[from,to)`, частичные часы обозначены настоящими границами. Нули — только число найденных наблюдений, при `coverage=unknown` они не доказывают отсутствие продаж.

## Почему пока нет тревог и прогрева по найденным заказам

В текущем коде есть свежесть источника сейчас и backfill существующих заказов, но нет полного журнала покрытия исторических интервалов. Возраст первого заказа или подключения не доказывает семь дней непрерывного наблюдения. Перечитывание сегодняшних mutable проекций также не восстанавливает всё прошлое состояние при удалении/изменении заказа. Поэтому отчёт возвращает `baseline_state=unknown`, `warmup_stage=unverified_history`, `alerts_enabled=false`; свежий heartbeat эту оценку не повышает.

Следующий срез: хранение доказанного покрытия и исключений истории (сбои, паузы, акции, праздники), затем ступени 7/14/28 дней и расширение окна при малых числах по ADR 0090. Пороги требуют калибровки на реальных данных до выпуска; здесь нет скрытого статистического порога или оценки потерь. Исторические величины в диагностике нельзя выдавать за статистически принятую норму или гарантию работоспособности покупок.

## Границы

Команда требует явные tenant/store и live/test; нет режима «все клиенты». Она предназначена для локальной диагностики и будущей калибровки, без HTTP endpoint, cron и автоматического включения для клиентов. Нет новых миграций, пользовательских данных или изменений API/event-контрактов. Growth+ и сроки хранения новой функции будут включаться по готовности, без изменения действующих опубликованных тарифов этим срезом.
