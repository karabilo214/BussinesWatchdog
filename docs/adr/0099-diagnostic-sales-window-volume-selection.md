# ADR 0099: Диагностический выбор окна по ожидаемому объёму заказов

Дата: 2026-10-30. Статус: следующий срез задачи 12.B, Step 332, в рамках ADR 0090–0098. Порог объёма из ТЗ §16 используется как исследовательский default, не как калиброванная статистическая уверенность.

`sales:history` v8 / same-weekday-bands-v4 добавляет order_baseline.window_selection. Для каждого реально существующего часового UTC-интервала целевого локального дня алгоритм выбирает первое окно из 1/2/12/24 номинальных часов, которое содержит интервал целиком и имеет предусмотренные ступенью кандидаты с достаточным ожидаемым объёмом. Это фиксированные локальные полосы ADR 0096–0097, не скользящий онлайн-интервал детектора и не проверка фактических продаж текущего часа. Широкая полоса может включать ещё не прошедшую часть целевого дня: здесь выбирается горизонт исследовательского профиля, тревоги не оцениваются.

Default min_expected_orders=20 взят из ТЗ §16, а не получен из реальных данных. Новая необязательная CLI-опция `--min-expected-orders=<положительное целое>` позволяет воспроизводимую калибровку; принимает каноническую десятичную строку без ведущих нулей, дробей, экспоненты или знака. Действующий минимум и default записываются строками в версионированную policy sales-window-volume-v1 каждого отчёта. Значение не сохраняется как правило клиента, не меняет тарифы или cron; нового ручного действия владельцу для выпуска нет.

Сначала используется структурная проверка SalesWarmupProfile. collecting, неизвестный календарь, нехватка нужных weekday/парных суток не заменяются сырыми большими оценками. Для stoppage_only проверяется профильный кандидат, для major_drop — оба кандидата ADR 0098, для full — прямой weekday. Все кандидаты данной ступени должны удовлетворять `numerator >= min_expected_orders × denominator`. Это консервативное условие согласия по объёму: оптимистичная из двух оценок не подменяет меньшую. Оно не означает, что оценки согласованы статистически. Смешанных весов, выбора только большего кандидата или нового порога падения нет.

Дроби проверяются и сравниваются точно через BCMath scale=0, без float и округления. Неверная/нулевая denominator, отрицательная/нецелая numerator не дают sufficient и не вызывают ложную нулевую норму. Для каждого проверенного окна сохраняются ключ/UTC-границы, оценки всех кандидатов, meets_minimum и причины. Структурно отсутствующие данные имеют volume_state=unknown; корректный, но малый объём — insufficient; достижение порога — sufficient только по объёму. Первое sufficient даёт selection_state=selected; иначе selected_window=null и abstain с причинами проверенных ширин. Пример: 10 ожидаемых за час и 20 за два часа выбирают два часа; один ожидаемый заказ за сутки не становится основанием почасовой тревоги.

Сопоставимость исторических образцов остаётся в ADR 0097–0098. Выбор содержит часовой интервал по реальным UTC-границам [from,to); нельзя брать соседнюю полосу только потому, что в ней больше продаж. Повторный час — две отдельные точки выбора с occurrence=1/2 и разными границами. Отсутствующий час не создаёт точку выбора; missing_bands сохраняется в базовом отчёте. Изменение минимума не меняет историю, покрытие, пометки или расчёт кандидатных оценок.

volume_state=sufficient / selection_state=selected не разрешают детектор и не закрывают статистическую достаточность. MAD=0 остаётся диагностикой, не основанием делить на epsilon. statistical_state=uncalibrated, общий baseline_state=unknown и alerts_enabled=false сохраняются. Нет сравнения с фактом, p-value/процента уверенности, финансовой оценки потерь, инцидентов или уведомлений. Реальная калибровка модели и порога, проверка дисперсии/устойчивости, скользящие окна, lag allowance, подтверждение нескольких окон и сам детектор остаются открытыми; ACC-44–47 не закрываются целиком.

Миграций/DDL, HTTP/event-контрактов, UI/плагинов, пакетов, env, юридических правок или действий на production нет. Команда остаётся read-only с обязательными tenant/store/mode; внешние системы не вызываются. Сервис выбора работает с уже scoped счётчиками, денежных полей не читает.
