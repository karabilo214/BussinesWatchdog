# ADR 0040: Parallel integration sync and reconciliation at scale

Status: implemented (Step 112); the nightly policy (point 5) and the history rule (point 4) were chosen by the owner on 2026-10-12

## Context

The owner pointed at two limits (2026-10-12). Integration syncs ran one integration after another inside one scheduler command: at ~2 s per integration, 1000 Stripe integrations take ~33 minutes per run while the command is scheduled every 15 minutes. Reconciliation took at most 100 subjects every 30 seconds in one process (≤ 288 000 a day), while the nightly sweep re-queued every order of the last 90 days (TZ §14, ADR 0003 point 3) — about 900 000 orders a night for 1000 stores with 10 orders a day. Every evaluation also wrote a new run with its findings even when nothing changed, and the "current findings" were computed with a window function over the whole history.

## Decisions

1. **Sync jobs**: `stripe:sync`, `paypal:sync`, `woocommerce-api:sync` and `shopware:sync` (all modes) only request one `SyncIntegration` job per eligible integration, oldest successful sync first, on the `sync` queue (Redis). Any number of `queue:work redis --queue=sync` workers run them. A job is unique per integration and mode while queued (a repeated request is dropped) and never overlaps another job of the same integration in any mode (`WithoutOverlapping`, released after 60 s, lock expiry 15 min; job timeout 840 s, `retry_after` 960 s). A job re-reads the integration and skips it if it is no longer eligible. `--inline` keeps the old in-process behaviour for a manual run without workers.
2. **Reconciliation workers**: `reconciliation:work` claims small batches (25, lease 300 s) of due dirty subjects, processes them and claims again, sleeping while nothing is due; several run side by side — on PostgreSQL the claim uses `FOR UPDATE SKIP LOCKED`, so workers never wait for each other's rows; each exits after `--max-time` or on SIGTERM for a clean restart. The scheduled `reconciliation:process-dirty` remains as a single extra pass. The Docker image gets `pcntl` (needed for signal handling and for queue job timeouts).
3. **Marks during processing**: a mark that arrives while its subject is being processed now asks for its own due time (30 s for an event, the deadline for a grace re-check) instead of keeping the subject's past due time. Before, a pending order was re-claimed on every pass until its grace deadline.
4. **History only on change** (owner's choice): `reconciliation_subject_states` holds the current result of every subject (order or store unmatched-payment scan): run, result hash (findings under the algorithm/config version), worst status, finding count, the plan entitlement and store-data freshness seen, `evaluated_at` (last check) and `changed_at`. An evaluation with the same result only moves `evaluated_at`; a different result writes the run and its findings and becomes current. Incidents are correlated only for a changed result — a mismatch the customer closed by hand is not reopened by an unchanged re-check (before, a nightly re-check opened a new incident and notified again a day after the close). Current findings (cabinet, CSV export, order card) come from the current state, which also fixes a stale display when the newest result had no findings. Existing data is backfilled from the latest completed run per subject.
5. **Nightly sweep** (owner's choice; replaces ADR 0003 point 3): within the 90-day window it queues only orders whose result can differ — never checked, still pending or unknown, changed after the last check (`orders.updated_at`), checked under an older algorithm/config version, or checked while plan entitlement or store-data freshness differed from now — plus the longest-unchecked orders whose last check is older than 30 days, at most a thirtieth of the store's window per night (at least 100), so every order is fully re-checked about once a month. Store scans and unlinked-capture matching run for every store as before. Coverage changes and connector recovery still re-queue the whole window of the store immediately.
6. **Scanner query**: the unmatched-payment scan excludes allocated captures with a subquery instead of loading every allocation id of the store into the statement (which would hit PostgreSQL's 65 535-parameter limit on a large store).

## Measured (local, PostgreSQL 18 in Docker on the development Mac, 6000 orders)

One worker: ~62 orders/s when results are written, ~119 orders/s when unchanged; four workers on the same machine: ~290 orders/s unchanged (the machine is the limit). One order evaluation is 10 SQL statements. Before: at most 100 per 30 s. These are local figures, not a production benchmark.

## Consequences

- Production must run queue workers: without a `sync` worker integrations are no longer synced (the scheduler only requests jobs). Docker Compose has `sync-worker` and `reconciliation-worker` (`BW_SYNC_WORKERS`, `BW_RECONCILIATION_WORKERS`, 2 each by default).
- History shows changes, not every check; "checked at" lives in the state. A full-window re-queue on coverage change still evaluates every order but writes only the changed ones.
