# ADR 0100: Завершённые скользящие окна продаж, явный lag и контекст истории

Дата: 2026-10-30. Статус: диагностическая реализация следующего среза задачи 12.B, Step 333; продолжает ADR 0090–0099. Статистический тест, реальная калибровка и детектор не включаются.

## Время и интерфейс

Новая внутренняя read-only команда `sales:window` требует явные tenant/store/mode и `--lag-seconds`. По умолчанию mode=live; `--at` — текущее UTC-время с точностью до секунды, либо явный RFC3339. Будущее время и дробные секунды не принимаются. Принятого default задержки в ТЗ нет, поэтому команда не выбирает его за владельца. Ноль допустим для исследования. Lag — каноническое целое 0…2419200 секунд (28 дней); верхняя граница технически привязана к горизонту диагностики и не означает достаточность сохранённой истории. Старый journal при большом lag может не покрывать требуемые даты — это unknown.

`evaluation_time = at − lag`. Четыре интервала заканчиваются ровно в evaluation_time и имеют фактическую UTC-длительность 1/2/12/24 часа. Они не округляются к UTC-часу, локальной полуночи или календарной полосе и не включают будущую часть интервала. Политика часов elapsed-local-endpoints-v1 и явный lag записаны в JSON sales-rolling-v1. `sales:history` v8 остаётся отдельной диагностикой фиксированного профиля, без изменения его формата; общий строгий парсер RFC3339 выделен для обеих команд.

## Историческое сопоставление

Кандидаты заканчиваются в те же локальные hh:mm:ss на 28 завершённых датах перед локальным днём evaluation_time. Исторические границы получаются через реальные timezone transitions: проверяются локальные дата/время обоих концов, относительный сдвиг дат, число/порядок повторений каждого endpoint и фактическая длительность. Отсутствующий локальный endpoint, неодинаковое число повторений и другая длительность дают отдельные причины отказа. Обычный час после перевода сохраняется, а повторный не заменяется произвольно обычным. Полуночь относится к следующей дате как endpoint, но [from,to) не включает её в перечень затронутых дней. Получасовые и 45-минутные смещения сохраняются точно.

Каждый затронутый исторический локальный день должен быть полностью покрытым после first_observed_at, с ready календарём, без исключений. Для прямой weekday-выборки сравнивается вся последовательность comparison_weekday затронутых дней; праздник целевой даты — воскресенье по ADR 0095. Например, переход воскресенье → понедельник не подменяется одним weekday конца. Неподдерживаемые календари не считаются обычными днями.

Все reference-окна заканчиваются не позже начала самого широкого проверяемого 24-часового окна (training_cutoff), чтобы наблюдения проверяемого периода не попадали в норму. Для прогрева по-прежнему используются 28 завершённых локальных дней, независимо от технического контекста. 7/14/28 и структурные 1/2/4 образца сохраняют ADR 0098.

Ранний профиль переносится на скользящий контекст явно: парный суточный знаменатель — сопоставимое завершённое 24-часовое окно, заканчивающееся в той же локальной точке, а не календарные сутки с будущими часами. Оценка = медиана этих 24-часовых объёмов нужного weekday-паттерна × сумма заказов коротких окон / сумма парных 24-часовых объёмов. Парные окна обязаны быть покрыты и не пересекаться с проверяемым периодом. Если контекст не наблюдался, профиль не создаётся из одного backfill. Перенос формы времени суток и этот rolling-кандидат требуют реальной калибровки; веса между прямым и профильным кандидатами не вводятся.

## Технический запас двух дней

Самый ранний из четырёх одинаковых weekdays для rolling 24h может начинаться раньше первой из 28 дат окончания образцов. Без контекста четвёртый суточный образец был бы недостижим даже при полном прогреве. Поэтому sales_coverage и сохранённые sales_baseline_exclusions теперь удерживаются по началу локального дня минус **30 дней**, плюс текущая часть дня. Два дополнительных дня нужны только для начал окон/сопоставимых суточных знаменателей, включая DST-переход через дополнительные локальные даты.

Норма остаётся по 28 датам окончания, счётчик прогрева остаётся максимум 28; технические дни не создают новые endpoint-образцы и не ускоряют ступень. Старые пометки сохраняются вместе с покрытием и проверяются для контекста. Диапазон ручного customer API/интерфейса остаётся 28 дней и сегодня; скрытый контекст не расширяет редактируемый диапазон. Уже срезанный прежним кодом журнал не восстанавливается автоматически без нового полного чтения. При смешанных версиях старый финализатор может срезать запас до 28 дней, а новый читатель честно даст unknown/меньше образцов. JSONB v1, таблицы и имена полей не меняются; миграций/DDL нет, предыдущий reader/writer совместим.

## Покрытие, факты и границы выводов

Фактические заказы считаются по source_created_at в [from,to), после tenant/store-scoped выбора последней проекции; mode/synthetic/deleted фильтруются после ранжирования. Один cursor по отсортированным timestamp считает префиксы на границах всех окон, без загрузки массива заказов в память и без отдельного сканирования на каждый образец. Поздние/исправленные проекции меняют повторный отчёт: это чтение текущего состояния, не архив состояния системы на момент at. Нагрузочная приёмка и согласованный snapshot для будущего online-детектора остаются отдельными gate.

orders_created_observed — число найденных проекций. orders_created становится числом только при непрерывном подтверждённом наблюдаемом покрытии фактического окна; иначе null, даже при observed=0. Lag не заполняет разрыв и не обходит inbox/revision barrier. Историческая модель показана отдельно от модели, допущенной к выбору окна: при unknown/awaiting_projection факта последняя блокируется. Достаточная норма сама по себе не разрешает сравнение без данных проверяемого периода.

Используется объёмная политика ADR 0099, версия sales-rolling-volume-v1: минимальное завершённое окно с достаточным объёмом всех кандидатов ступени и подтверждённым фактом. min_expected_orders=20 остаётся явным draft-default с необязательным override. Пауза/акция/data_gap целевого интервала блокируют сравнение; holiday и local_day_boundary не блокируют его сами по себе при корректном сопоставлении. Текущий incident сохраняется в метаданных, но не запрещает наблюдать его период и не закрывается отчётом; исторические дни incident по-прежнему исключаются из нормы. Без этого будущая проверка восстановления могла бы заблокировать сама себя.

Нет статистического verdict «продажи упали/работают», p-value, оценки потерь, инцидентов, уведомлений, cron, новых env, UI/плагинов, тарифов, внешних запросов или изменений юридических страниц/production. baseline_state=unknown, statistical_state=uncalibrated и alerts_enabled=false сохраняются. Остаются статистическая проверка, устойчивость/дисперсия, калибровка lag/модели/порогов на реальных данных и online-жизненный цикл детектора. ACC-44–47 целиком не закрываются. Новые команды — внутренние исследовательские инструменты, ручных release-действий владельцу не добавлено.
